# Open questions and what the shipped software settles

<!-- keep -->

The hardware headers mark what they do not know with "not known", "unknown" or an `UNKNOWN` label. This page is the ledger for those marks. Each entry says whether the shipped software settled it, the evidence, and for what is still open, what would settle it.

Grades are established, secondary, inferred or unknown; the legend is in [AGENTS.md section 7](../AGENTS.md#7-published-documents). None of these is a measurement of the silicon. Binary evidence is cited by object and text offset in the 6.5.22 kernel graphics objects (`mgras.o`, `mgras_init.o`, `mgras_mco.o`). The diagnostics are the 6.5.7 standalone graphics diagnostics and their option-board command registry.

This pass covered the host interface, the board-level words and the multi-channel option, and later passes (entries 6 to 14) took more of the open marks. It did not examine the texture engine marks, the geometry-engine operation codes or the vertex-path marks; they are listed under "Still open" with the evidence that would settle them.

## Settled in this pass

### 1. Multi-channel option register map

Question: "what the option board's index values control" (board header, display control bus device 11). Settled. The kernel object that loads the option (`mgras_mco.o`: probe at text offset 0x0, FPGA load 0x30c, the two DAC loaders 0x590 and 0x96c, timing chip 0xb24, device 11 timing word 0x11a0, control registers 0x127c, ADV7162 register pointer 0x1328) uses a byte index port and a byte data port, and the index is a bank in the high nibble and a port in the low:

| Index | Target | Grade |
|---|---|---|
| 0x2n, 0x3n | ADV7162 true-colour DACs, channels 1 and 2 | established |
| 0x0n, 0x1n | ADV473-class overlay-palette DACs, channels 3 and 4 | established |
| 0x80, 0x90, 0xA0 | board control registers 1, 2, 3 | established |

The bank bases come from a five-entry per-channel table in the object's initialised data (0, 0x20, 0x30, 0, 0x10 for channels 0 to 4). The part names come from the loader routine names and the option's diagnostic command list (the registry lists 7162 and 473 palette tests). Ports on an ADV7162 channel: +0 is a 10-bit register pointer written as two bytes; +1 the palette data (256 entries of six bytes, each colour's high 8 bits then its low 2 bits); +2 the data port of the register the pointer selects; +3 the part's mode register (MR1, settled below). Reading register 3 returns 0x79 on a healthy part (the kernel compares), so register 3 is the identification register; the ADV7160/ADV7162 data sheet (Analog Devices, Rev. 0, 1995, SHA-256 `c8fa1a6dfc22...3c24`, page 27) agrees: 79H for the ADV7162, 76H for the ADV7160.

Port +3 and the register numbers, settled by the data sheet and the loader together. The sheet (Figure 33, page 22; Figure 34, page 23) gives the part four MPU ports chosen by two select lines, C1 and C0: 00 the address register (written low byte, then high byte), 01 the palette data, 10 the control register the address register points at, 11 the mode register. The loader's ports +0, +1 and +2 do exactly the first three, so +3 is the fourth. In `mgras_mco_config_7162` (text offset 0x590; `retools/tools/hostfacts.py` on the `mgras_mco.o` member of the IP28 `mgras.a`, object sha256 `9ce7195504086119...829f`) the loader writes index byte bank+3 at 0x63c, then to the data port the bytes 3 (0x66c), 2 (0x670) and the first word of the caller's configuration block (0x678), reads the data port back at 0x69c and compares it with that word (a mismatch returns -5, 0x6a8). The sheet's initialization sequence (page 38) writes the mode register three times, xx000xx1, xx000xx0, xx000xx1, and its bit MR10 resets the pixel-port sampling sequence by "writing a 1 followed by a 0 followed by a 1" (page 26); it also says the mode register can be read back. The loader's 3, 2 and caller word fit that pattern (low bit 1, 0, then the caller word's own low bit). MR11 = 1 selects 10-bit palette and DAC resolution and MR12 = 0 an 8-bit bus, which match the loader's six-byte palette entries (8 high bits, then the 2 low bits). Grades. Established: the write, read-back and compare sequence on port +3; the part's port selection, the mode-register reset sequence and the register names below, from the sheet. Inferred: that the option board's index low bits are wired straight to C1 and C0 (the board glue is not documented; ports +0 to +2 behave as 00, 01 and 10 and +3 is the remaining value). Unknown: what the caller's first configuration word holds, since the per-video-format table it comes from is outside this object.

The loader's register-pointer values have data-sheet names (Figure 34, page 23): 3 identification, 4 pixel mask, 5 command register 1, 6 command register 2, 7 command register 3, 8 command register 4, 9 PLL command, 0xC PLL reference divider, 0xD command register 5, 0xF PLL feedback divider, 0x204 cursor control. The loader writes registers 5, 6, 7, 8, 0xC, 0xF, 0x9, 0xD and 0x204 from words 1 to 9 of the configuration block (accesses at 0x710 and 0x7a4 to 0x8d0) in that order; the sheet's recommended initialization lists the same registers in another order and adds register 4. Established for the numbers and names. The meaning of each bit of each block word depends on the caller's table, which is not read here. Ports on an ADV473-class channel (graded: +0 and +1 established, re-read this pass in the option's 473 loader and 473 gamma loader, which write the palette address to port 0 and then three bytes per entry to port 1, one byte each from three 256-entry colour tables; +6 is established as a write of one value from the caller's first word at index base + 6, re-read in the 473 loader's machine words, and its role as the command register is inferred; `devices/mgras/registers.toml` now carries these ports as bank-relative port numbers): +0 palette write address, +1 palette data (three bytes per entry), +6 command; +2 is inferred to be the pixel read mask because the display server writes it (0 or 0xFF) in its blanking sequence and the family's register order puts the mask there.

The option also has an FPGA configuration path (data byte at display-bus register select 0, control and status at 1) and its own timing chip (select 4 picks a register, select 5 is its 16-bit data, select 7 the auto-incrementing timing RAM). The FPGA load checks status bits 2:0 as 000 after the first control write (0xFE), 110 after the second (0x01) and after every data byte, and bits 1:0 both set after all 0xF688 bytes and 20 zero padding bytes. The board-ID probe at the start of the same object has two shapes, one per CPU board family, and both readings that have been written here were right for some build and wrong as a general statement. See "Board-ID probe, per build" below; do not state the probe without naming the build family.

### 2. Blanking mask register

Question: "which DAC register the display server's blanking writes reach". The display server writes register pointer 4 (bytes 0x04, 0x00) of the same ADV7162 and then 0x0000 to blank or 0xFFFF to restore. Established: it is register 4 of the ADV7162, written 16 bits wide. Established, from the data sheet (Analog Devices ADV7160/ADV7162, Rev. 0, 1995, Figure 34 on page 23 and the Pixel Mask Register text on page 27): register 004H is the pixel mask register, an 8-bit read/write register whose bits are individually ANDed with the red, green and blue pixel input stream, FFH for normal operation. So 0xFFFF restores and 0x0000 blanks by masking every pixel, as the earlier reading said. The register is 8 bits wide; the 16-bit width of the display server's store is a bus-access width, and what the part does with the upper byte is not stated in the sheet (unknown, no effect on the blank and restore result). The register is named `DAC_ADDR_PIXMASK` in `CMAP.h` (reset value written by the drivers, 0xFF) and the blanking sequence in `MGRAS.h`. This closes the question for the ADV7162 channels; the ADV473-class channels' port 2 stays inferred (no data sheet for that part is held).

### 3. Host interface error causes

Question: the flag register's causes beyond the ones named. Settled for four. The kernel's general interrupt handler (`mgras.o`, text offset 0x8378) tests the group 0xE200 and, in order, prints a microcode error (bit 9), a DMA address range error (bit 13), a command-FIFO privilege violation (bit 14) and a DMA access or stack overflow (bit 15), clearing each through the interrupt-enable clear register. The messages are matched to bits by the handler's string-pointer offsets, which land on consecutive strings in the object's table in the same order; the interrupt enable the kernel programs at boot (`MgrasInitialize`, right after `MgrasInitHQ`), 0x4400E200, contains exactly this group plus the two FIFO high-level bits. The same handler also uses bit 16 (sync complete), bit 19 (context saved), bit 6 (context loaded) and bit 10 (buffer swap), which agree with the headers.

Changed: the old `error` reading of bit 8 is dropped from the header, and the matching `error` field and flag macro are removed from `devices/hq3/registers.toml` and `HQ3.h`, so bit 8 is now unplaced everywhere. The handler never tests bit 8, and the diagnostics' walk of the flag registers masks 25 bits (0x1FFFFFF), so there are 25 flag bits in all.

Still unknown: what raises flag bit 20. The kernel enables it at start-up (the flag-enable value 0x11000F is bits 3:0, 16 and 20). The buffer-swap path (`mgras.o` text offset 0x402c) reads bit 20 from the flag register, clears it and flushes the command FIFO. Reading how the microcode raises it, from the host interface microcode (`hq3.u`), would settle it.

### 4. Host interface values the kernel programs

Question: the headers listed watermark defaults "older notes recorded" and said the drivers program others. Established: `MgrasInitHQ` (`mgras_init.o` text offset 0xfac) writes configuration 0x7E8C (OR the caller's bits), GIO configuration 0x765B900F, command-FIFO high 0x20 (less twice a per-board count when that is positive) and low 0x14, delay 0x64; data-FIFO high 0x28, low 0x14, delay 0xFFF; bus-FIFO low 2, high 6, delay 0x8C; flag enable 0x11000F; and clears every cause and enable first. Its caller then writes the interrupt enable 0x4400E200. The information-gathering routine (`mgras_init.o` text offset 0x8a8) writes the configuration as 0x7E8D, the same value with bit 0 set. The standalone diagnostics program 40 and 20 with delay 100 for both command and data FIFOs and 8, 2, 100 for the bus FIFO. The two sets are now separate constants in `devices/hq3/registers.toml`. The configuration register is 15 bits on this chip (the diagnostics test it with mask 0x7FFF; 0x3FFFF on the later host-interface part), so bits 14:9 of the init value are real state; their meaning is unknown, and a register description of the host interface or a write/read-back probe would settle it.

The GIO configuration value decodes against fields the headers already define (bits 3:0 and 12 set, bit 6 clear) and against the bus-master timing fields in `HQ3.h` (all set), which is consistent with those fields being real.

### 5. Board identification probe

The kernel's probe (`mgras_init.o`, text offset 0x770) accepts a board only if the first word has bits 6:0 equal to 0x10, bit 16 set, bit 17 clear and bits 31:18 equal to 1, and does not look at bits 15:7. The word the headers record, 0x00050190, passes. Bit 7 is not checked; bits 6:4 must be 001, and bits 15:8 are not compared by the probe; the information-gathering routine later saves bits 15:8 as a one-byte board field. The headers' revision and product split is established from the GIO BUS Specification, version 1.1 (draft), 7 April 1992, sections 2.10.1 and 2.10.2: product ID code in bits 7:0, revision in bits 15:8. The PDF's running page headers read "GIO32 Specification, 6 May 1992". The probe fixes only which bits are compared.

### 6. Framebuffer size register, top byte

Question: what the top byte of the DRB size register (pixel processor register 0x16E, traced as 0x90 under 6.5.22, per `PP1.h`) means. Settled in the sense that it is not a programmed setting. The kernel routine that writes the register (`MgrasSetRSSTiming`, `mgras_init.o` text offset 0x21b8 in the 6.5.30 object and 0x1fe8 in the 6.5 base object) builds the value in a register from the screen width and the raster-engine count: it replaces bits 1:0, 5:2, 7:6 and 9:8 in turn and clears bit 10. It starts from a word it loads from its own stack frame at offset 0 (`mgras_init.o` text offset 0x2280, 6.5.30; 0x2084, base), and nothing in the routine stores to that slot before the load: the only stores to the frame are the saved registers at offsets 8 and up, and the slot's address is never taken. So bits 31:11 of the written value are whatever an earlier call left on the stack, not a value the driver chose (inferred from the code; both objects have the same shape). The write is one 64-bit store into the board's command window at board base + 0x120400, the upper word a fixed command naming register 0x16E (command word 0x00196E04, read from the object's 8-byte constant table) and the lower word the value. The same routine then writes register 0x16D from a word in the timing table (offset 0x6c), with the command word 0x00196D04, also from the constant table.

Why this matters: the 0x90 the 6.5.22 trace shows is stable across the two boards traced, which fits a deterministic leftover from the preceding calls and does not need a hardware meaning. The standalone diagnostics and the boot-time info routine never set the top bits (the low words at 1024x768 are 0x31A for one raster engine and 0x25A for two, as `PP1.h` and `devices/pp1/registers.toml` record them, and re-reading the routine in the 6.5.0 kernel object (sha256 `8369b6d4a250d395123793a8dd339bfa0f158caa32cbf218fdb76a904725c9d7`) reproduces both from the width and the engine count: the two tile divisors 768 and 192, the engine count compared with 2, and the line-count field 3 unless the count is 2, when it is 2. The 0x90 top byte comes from the 6.5.22 trace, whose source was not re-read in this pass, so the full words 0x9000031A and 0x9000025A are not independently established; an earlier draft of this entry wrote 0x31E and 0x25E, which was a transcription error, since bit 2 set would make the 192-pixel tile count 7 where 1024 pixels give 6; corrected; the low bits are established from the routine), and the register still works. The headers now say the top bits are unprogrammed and unknown.

Still unknown: whether the pixel processor ignores bits 31:11 or latches them. Settling test: write the register with the top byte 0x00 and with 0x90 on a board and compare a full-screen fill and a read-back; or read the register on a board that has not had a driver run.

### 11. Command-stream tokens 0x096, 0x097, 0x0DA and 0x05F

Question: the meaning of the tokens the header lists as "meaning not known". Narrowed, not fully settled; the hardware meaning lives in the host-interface microcode, which I did not decode (the microcode object carries only a line table, no labels).

- 0x096 and 0x097 are a bracket (established, from the 6.5.0 graphics library's pixel read-back entry points): `glReadPixels`, the colour-table copy and the slow copy path send 0x096, run the read-back routine, then send 0x097. So 0x096 starts and 0x097 ends a pixel read-back, and glCopyPixels and glCopyTexImage2D use them because they read the framebuffer through the same routine. The header's note that they appear together in those calls is consistent.
- 0x0DA (established that it follows the wait for a board-to-host transfer): the DMA read-back helpers set up the transfer, spin on bit 1 of the user status register (0x70000), then send 0x0DA with no operand. The texture read path does the same after its own read transfer, and one path follows it with the raster state restore. Inferred: it releases the pipeline after a read transfer completes; what the microcode does with it is unknown.
- 0x05F carries one operand word that is not a GL enum, contrary to the earlier note (established): the texture manager sends it with operand 0 right after the texture mode is saved aside and before the texture-off token (0x00C); the enable and disable entry points send it with operand 0 or 0xE0100 in the same position when they switch texturing, and a GL enum goes out under other tokens (corrected: an earlier reading put the texture enum under 0x0A7, but in the 6.5.0 library, sha256 `eca0027567a5ae885ca2a996349ef838c07364c6c2e7535ba65076eb359a5c2e`, read with `retools/tools/hostfacts.py` and the disassembly of the disable entry point, 0x0A7 is sent only with the clip-plane enums 0x3000 to 0x3005, and 0x0A6 likewise from the enable entry point, which agrees with `HQ3.h`; established for that build; which token carries the texture enum was not read); and the routine named for sending the second texture-mode word sends it with 0.0 or plus or minus a float taken from the texture environment state. Inferred reading: 0x05F stores a second texture-mode word in the geometry engine, and the texture manager clears it while a load runs. The enable and disable association in the table comes from the first function that happens to send the token and is not its meaning.
- 0x0EB: not found as a command word in the 6.5.0 graphics library. The library's 0xEB is a different number space (a module identifier for the pixel-path state, installed with the zoom-state initialiser), so it cannot be used to name the token. Still open.
- Geometry-engine word 3: not examined.

What would settle the rest: the host-interface microcode read for the handler each token index jumps to (decode the 24-bit instruction word, then follow the token dispatch table), or an operand-level trace, taken from a board, of one texture load with each token removed.

### 12. Transfer mode register, bits 17 to 21

Question: positions of the unpack-order and read-mask flags. Not settled; two statements in `RE4.h` were wrong and are corrected.

- The 6.5.0 graphics library's default-state routine ORs 0x40000 (bit 18) into its transfer-mode shadow at context creation (the decompiled 6.5.0 library's default-state routine, `__glMgrasInitDefaultValues`). The header said the library never sets bit 18. The two copy initialisers (raster to raster, `__glMgrInitRSSToRSS`, and raster to texture, `__glMgrInitRSSToTE`) clear bits 17, 18, 19 and 20 one at a time and set bit 23. The DMA read helpers build their transfer mode word from the same shadow with only the format, skip and stride fields rewritten, so a GL read-back DMA carries bit 18 unless a path clears it. The "PIO read order" reading of bit 18 therefore cannot be the whole story: bit 18 is a mode flag the library sets by default and clears for copies.
- The stride-skip field is three bits wide in every writer I read (mask 0x1C000, bits 16:14; the X server uses `& 7` too), not four. Bit 17 is a single-bit flag that the same initialisers clear; nothing sets it.
- Bit 21 is never written or cleared by anything I read (library, X server, diagnostics). The diagnostics only ever set the format, type, skip and stride fields and the RGB-order bit; they never set unpack-order, zoom, decimate or read-mask.

Update: the read routine for glReadPixels (`__glMgrDoReadPixels`, 0x0da58880 in 6.5.13f, 0x0d9688d0 in 6.5.30m) is one of the paths that clears bit 18 (see entry 17), so a read through it does not carry the default.

So the unpack-order and read-mask flags are among bits 17, 18 and 21 (inferred by elimination; 19 and 20 are fixed by the trace as zoom and decimate, 22 as RGB order, 23 as opaque). Settling test: write each of bits 17, 18 and 21 on its own with a known two-pixel PIO transfer, on a board, and see whether the byte order within a word, or a masked pixel, changes.

### 13. Line endpoint flags

Question: positions of the first and last endpoint flags in the instruction register. Semantics settled, positions not. The 6.5.7 diagnostic line test sets both flags to 1 exactly when line smoothing is enabled and to 0 otherwise, for the sub-pixel GL line opcode. Inferred: the flags mark the endpoints of an antialiased line for special end handling. The compiled diagnostic is stripped and builds the register with bit-field arithmetic I could not isolate, so the bit numbers are still unknown (bits 3:0 are the opcode and bit 4 is setup; the flags are somewhere above, most likely adjacent). Settling test: issue one smoothed GL line with a candidate bit set at a time in bits 5 to 8 and see which changes the coverage of the end pixels.

### 14. Crosstalk widget register defaults (Octane host interface)

Question (reset values row, narrowed): the register defaults for the Octane host interface's crosstalk widget block. The Octane build of the standalone diagnostics (`ide`, IP30 build) has a default-check table of eleven widget registers with the expected value, an access mode and a mask for each. I read the table directly out of the shipped binary (data segment at file offset 0x1431e0, 24 bytes an entry): identification 0x0E001D55 (read only, 32-bit), status 0, error address high 0 (16-bit mask), error address low 0, control 0x32F (read/write), request timeout 0xFFFFF, interrupt destination high 0, interrupt destination low 0, error command 0, link-layer configuration 0x03FF1810 (maximum burst 16, null timeout 6 in bits 15:10, retry limit 0x3FF in bits 25:16), target flush 0. Grade: established that the diagnostic expects these after power-up (it prints an error for each register that differs); inferred that they are the hardware reset values. The identification word does not decode cleanly as a standard widget identification (its part-number field is 0xE001, while the diagnostic's own part constant is 0xC003), so treat that word as the diagnostic's expectation only. Grade: unknown whether the mismatch is a different part revision, a deliberately different expectation, or a misread of the field split. Settling test: read the diagnostic's own part constant at its use site in the `ide` binary with `retools/tools/hostfacts.py`, and compare the identification register value in an existing Octane console capture of a widget probe. The host-interface registers the decode headers cover (`devices/hq3/registers.toml`) are separate and stay `reset=unknown`.

### 7. Context image bank words and flags

Question: the context image's word 1 bits 26 and 28, and words 16-17 (`HQ3.h`). Settled for bit 26 and words 16-17; bit 28 narrowed. ### 9. Pixel transfer zoom registers

Question: the encoding of the two zoom registers (0x154, 0x155) and what the mode bits 19 and 20 of 0x159 mean. Narrowed: the client's side is settled (below); what RE4 does with each word is not.

**Client arithmetic, established** (6.5.30 IP27GR532 `libGLcore.so`, `__glMgrInitHostToRSS` 0xd9641b0 and the state setter `__glMgrim_PixelZoom` 0xd96cc10, both read in full; the 6.5.0 IP28GR432 build has the same constants and shifts, not re-read in full). The setter keeps, in a state structure of the context, a replication count n at +0x1a0, a factor at +0x1a4 and a mode code in bits 29:28 of the word at +0x1ac: code 1 for a whole-number |x zoom| (n = 1, factor trunc(256 |z|), 0x100 at zoom 1), code 2 for a non-whole |z| above 1 (n one of 2, 3, 4, 6, 12, 24 chosen by the size of |z|, factor trunc(256 n / |z|)) and code 3 for |z| below 1 (n = 1, factor trunc(256 / |z|)). `__glMgrInitHostToRSS` reads them back and sets mode bit 19 of 0x159 only for code 1 with |z| above 1, and mode bit 20 for every other case except |z| = 1 (below 1, and code 2). Its four outcomes:

| Case | 0x155 | 0x154 | 0x159 bit 19 / 20 |
|---|---|---|---|
| transfer kind 5, 6, 7 (span read, span return) | 0x100 | 0x100 | 0 / 0 |
| whole-number \|z\| above 1 | the factor, trunc(256 \|z\|) | the same word | 1 / 0 |
| \|z\| below 1, or non-whole above 1 | step = trunc(256 w n / D) | ((trunc(256 w n / step) - D) << 8) + step | 0 / 1 |
| \|z\| = 1 | not written | not written | 0 / 0 |

w is the source width and D the destination extent the routine computes from the raster position and the zoom (trunc of the position plus the zoomed far edge, minus trunc of the position plus the near edge), so for an aligned draw D = w |z| and step = trunc(256 n / |z|). A model run of the 6.5.30 client in the Origami repository (16-pixel rows, zooms 0.5, 1.5, 2, 3.25) shows 0x200, 0x155, 0x200 and 0x13b in both words with bit 20, 20, 19, 20; those are the formulas' values (341 = 256 x 2 / 1.5, 315 = 256 x 4 / 3.25) and corroborate the code, but a model run is not board behaviour. The 0x159 words 0xd00080 and 0xc80080 that run shows appear in no binary because the routine ORs bits 19 and 20 into a word it keeps in the context; the zoom values do not appear as literals for the same reason.

Three things that earlier notes had wrong or open, resolved from that code. (1) Bit 20 is not only "zoom below 1": the client also sets it for non-whole zooms above 1, where the factor is a source step over the replicated source (n copies of each pixel, step = n / |z| in source pixels). That the geometry engine does the replication is inferred. (2) 0x100 is not the "no zoom" pair of a pixel draw. Only the kind 5, 6, 7 shortcut writes it. A draw at x zoom 1 never stores either frame word before the register writes (no store to either stack slot on that path), so 0x155 and 0x154 carry stale stack words with neither mode bit set: a traced 0x1000f424 with 0 at zoom 1 is that, not an encoding, and so are the pairs 0x101423AC / 0 and 0x3BFC00 / 0x1010090 recorded earlier from 6.5.22 runs (inferred: all three have the look of data addresses in the client's image). The withdrawal of those pairs as register values stands, now with its cause. (3) The decompiled formula in the previous version of this entry (source width over destination width) was right in form but missed the replication count n, which multiplies the source width.

Grades, after a disassembly check of the same routine in the 6.5.0 library: established that the routine writes register 0x155 from one frame word and register 0x154 from another, and that a path stores 0x100 into both words (the no-zoom pair). Inferred, from the decompilation only and not checked against the disassembly: the magnification and shrinking formulas above. ### 16. Host transfer table slots

Question: whether a table entry for slot 0 is a byte address or a 16 KiB page address, what picks the entry format per slot, and whether the kernel writes an entry per 16 KiB page. Builds: kernel graphics modules of 6.5.13f and 6.5.30m (`mgras_dma.o`, sha256 `98a9fa327434b730754b24825c265b3a038c3dfc809320cb8463dd53119b7799` and `ff13b61214353a469a0b820a8b84f0dba2cb87cc9b30f4f6c5ec6fc6fd27de82`).

Established from the machine words (read, not executed):

- Five table slots exist. The routine that installs a table (`MgrasInstallTxTbl_Kern`, text offset 0x1a4 in 6.5.13f) refuses a slot number of 5 or more and writes, for slot s, the host-address-generator registers 0x820 + 2s (table base, physical address from the kernel's own address translation), 0x82B + s (entry count) and 0x830 + s (largest pointer offset), and register 0x84B + s. In `HQ3.h` names these are image table 1 to 3 (slots 0 to 2), the GL table (slot 3) and the display list table (slot 4). The register constants are identical in both builds (the routine differs by one branch offset); the table-fill and request-check code is structured the same in both with different register allocation, and was compared by its constants and call structure, not instruction by instruction.
- A table is a kernel allocation of at most 0x800 four-byte entries (`mgrasGetTxTbl`, text offset 0x960, 0x800 entries by default, zeroed). The base register is programmed with the table's physical address plus 12 (`daddiu 0xc` in the delay slot of the translation call at text offset 0x12d4, in the request routine `mgrasDmaUtil`, 0xdfc), so the first entry sits 12 bytes into the allocation. Xsgi's slot-0 list address ending in 0x00C fits that; whether that list is this table or the request list below is not settled.
- Entries are four bytes, one per 4 KiB page, not per 16 KiB page. The fill routine (`mgrasFillTxTbl`, text offset 0xc14) takes a start address and a length, asks the kernel for the physical page number of each 16 KiB page the range touches (`curproc_vtopv`), and writes that number and then three successors one apiece (loop at 0xc80 to 0xcd8: `+1` per entry), starting at the sub-page `(address >> 12) & 3` for the first page; after the last page it pads the rest of the table with the last entry (0xcf4 to 0xd30). So a page number a table entry holds is in 4 KiB units, four per 16 KiB page, consistent with 4 KiB page numbers like 0x56c20 in slot 3's GL lists; it is neither a byte address nor a 16 KiB page number.
- Nothing selects an entry format per slot. The slot only picks the register triple above. Slots 0 to 2 and 3 to 4 differ in the request check: the request routine, on the path taken when the flag argument has bit 2 set, rejects a request whose list holds any address with low 12 bits set (the OR of all addresses is tested against 0xFFF, text offset 0xf94, error 22), and for slots 3 and 4 it applies an extra bound, a request length above 0x0FFFFFFF is refused (compare at 0x106c to 0x107c). The request list is an array of 8-byte user virtual addresses, 4 KiB aligned; the routine builds a per-entry length array of its own in which every entry holds the request's one common length rounded down to 4 KiB (store at 0x1178), and each address and length pair goes to the fill routine (loop at 0x1148 to 0x1204). The object imports an ABI-translating copy-in, so a 32-bit caller's 4-byte entries are probably widened on the way in (inferred; the copy was not read).
- That puts Xsgi's slot-0 value 0x49e5e000 in the request list: a 4 KiB-aligned user virtual address (not 16 KiB aligned: 0x49e5e000 & 0x3FFF = 0x2000; it sits in the same 0x49e5xxxx region as the list). The zero entries behind it are unused list slots (inferred: the count is an argument, and a zero address would be translated like any other). The 4 KiB page numbers in slot 3 are the kernel's output form. This reading, not a per-slot format difference, is the proposed answer; it assumes the memory read was of the request list before the call. Settling test: read the same list after the install call and see entry 0 replaced by a page number, or read the kernel's table through the board's base register value minus 12.

### 17. Transfer mode word of glReadPixels

Question: the bits of register 0x159 for a GL read split in two parts (0xC10080 then 0xC10480; 0xC00080 then 0xC10480). Builds: `libGLcore.so` of 6.5.13f (`b1fef785...`) and 6.5.30m (`7030d7b1...`), the read routine `__glMgrDoReadPixels` (0x0da58880 and 0x0d9688d0).

### 19. Host transfer table slots across context switches, requests and exit

Question: whether the kernel saves, restores or rewrites the table registers of entry 16 (host-address-generator registers 0x820 to 0x84F) when the pipe changes owner, on each request, or when a client goes away; and whether slots are owned per process. Builds: kernel graphics modules of 6.5.13f and 6.5.30m (`mgras.o` sha256 `7dac2718...` and `af04a6ba...`, `mgras_dma.o` `98a9fa32...` and `ff13b612...`). Text offsets are 6.5.13f first, 6.5.30m in brackets. Read from the machine words, not executed.

Established:

- Only `mgras_dma.o` writes the slot registers. A scan of every constant 0x820 to 0x84F in all sixteen graphics modules, `rrm.o` and `gfx.o` finds them only in `MgrasInitDMA` (0x0, once at board start-up, after which it polls and issues sync words), `MgrasInstallTxTbl_Kern` (0x1a4 [0x1a8]), `MgrasResetTxTbl_Kern` (0x28c [0x290]), `mgrasTeardown` (0x7b4 [0x7ac]), `mgrasDmaUtil` (0xdfc [0xdf4]) and the `MgrasDmaEdit*` routines. Nothing in the context switch routine `MgrasCtxsw` (0x7930 [0x7ac0]), the pipe-owner switch `MgrasPcxSwap` (0x3e60 [0x3e30]), `MgrasExit` (0x2690 [0x2630]) or the client teardown `MgrasDestroyDDRN` (0x2c7c [0x2c18]) writes them.
- The kernel's own saved state on a switch is the one in `HQ3.h` (configuration, bus configuration and enables to a kernel record, then the board's save routine by microcode address, then the 63-word image written through the user FIFO). Those 63 words carry no table base, count or offset: words 0 to 39 are the slot address, flags, window state, bank pair and the X server's raster registers, and 40 to 62 are zero in every traced image. So the kernel does not save or restore the table registers.
- The one switch-time touch is slot 2, the kernel's own table. `MgrasPcxSwap` calls `MgrasResetTxTbl_Kern` with slot 2 (call at 0x4854 [0x4778]; argument `addiu a1, 2` at 0x4850) on the path where the owner changes and the incoming context needs it, and `MgrasEramRead`/`MgrasEramWrite` (0xf54, 0x1224 [0xf18, 0x11f0]) and the overlap save and restore routines in `mgras_texsr.o` install slot 2 around each use (`MgrasInstallTxTbl_Kern` calls at 0xf90, 0x1260, and 0x2a4, 0x62c, 0x670 in `mgras_texsr.o` [0xf5c, 0x122c, 0x29c, 0x630, 0x674]). The reset writes the slot's base register 0x820+2s with 9, zeroes the count register 0x82B+s and the offset register 0x830+s, writes 0x84B+s, and follows with five sync words (0xE0100).
- Every client request rewrites its slot. `mgrasDmaUtil` first calls `mgrasTeardown` for the slot (call at 0xea8 [same]), which, when the slot holds a mapping, writes register 0x84B+s with the 0x180000 flag and five sync words (0x7f8 to 0x864), and clears the slot's software state. On success it writes the base (0x820+2s, physical address of the kernel table plus 12), the count (0x82B+s) and the offset (0x830+s) registers (0x12a8 to 0x1348). The slot registers are programmed only by a request, never by an event. A user kick that uses a slot without a new request does not touch them.
- Ownership. The software slot record is per open of the device: `mgrasDmaUtil` takes its record at the client's private structure (pointer at +0x70) plus 0x288 plus 80 bytes per slot, so two clients each have their own record for slot 0, but the table registers are one set per board. The last request to program a slot wins and nothing orders a later kick against it. Slot 1 is different: its record is a shared, counted pool (pointer at client private +0x470 plus 0x10), released only when its count falls below 2 (`MgrasDestroyDMA` 0x754 to 0x768). Slot 2 is refused for client requests: both request entry points compare the slot argument with 2 and return error 22 (`MgrasDmaUtil_Single` at 0x1450 [0x1434]; `MgrasDmaUtil_Multi` at 0x1668 and 0x16b0 in 6.5.13f; the 6.5.30m routine reads the slot at 0x1628, 0x166c and 0x1694, the compare itself was not re-read). Slots 0, 1, 3 and 4 are not restricted by client type: nothing in the ioctl dispatcher (`MgrasPrivate`, 0x5554 [0x55d0]; the calls at 0x64d0, 0x6518, 0x658c [0x6570, 0x65b8, 0x662c]) tests who is asking, so a GL client may take slot 0 (the library does for reads). A 32-bit caller's 4-byte list entries are widened by `copyin_xlate` (`MgrasDmaUtil_Multi` 0x15dc), which settles the inference in entry 16.
- Exit and close. `MgrasExit` (calls to `MgrasDestroyDMA` at 0x27c0 and 0x289c [0x2760, 0x2838]) and `MgrasDestroyDDRN` (0x2d50 [0x2cec]) run `MgrasDestroyDMA` (0x6f0 [0x6ec]), which for slots 4 down to 0 calls `mgrasReleasePoolMemory`, which unlocks the client's pinned user pages and frees the three per-slot arrays (`mgrasReleasePoolUserMemory`) and then the kernel table (`mgrasReleasePoolTxMemory`, kmem free of the table pointer). None of these routines, nor `mgrasTeardown`, is called here and none writes a slot register: after a client exits, the board's base, count and offset registers still hold the freed table's address (established from the code). Whether the stale registers matter depends on whether the board keeps those registers per context; see below.

Earlier reading (first pass, kernel only), superseded by the microcode read below: the kernel gave indirect weight to the microcode saving the host-address-generator context RAM (`HQ3_HAG_CTX`, 0x200 bytes at 0x50300, which holds these registers): the RAM sits beside the interface and bus ones, the kernel never rewrites slots 0, 1, 3 and 4 at a switch, and two GL clients that both program slot 0 would overwrite each other. That was inferred, not read.

Microcode read (second pass). Builds: the host interface microcode image `hq3_revB_HQ4.bin` of 6.5.13f and 6.5.30m (identical, sha256 `5305381f...`; the listings are `deed63f3...` and `a696e977...`, same code, different assembly dates), and the older image in the gr4 root (listing `2d35e2ec...`, banner 1998), whose save routine has the same layout at the same address. The jump, immediate and register-move forms are inferred from the data (the tool marks them with a question mark); nothing states the instruction set, so a reading below that depends on a form says so.

Established (machine words):

- Nothing jumps to 0x4FC: it is started only from the host, as the kernel does. So the table base, count and offset registers of entry 16 are in it. This is where the match to the register file is exact: 8-byte registers get 8-byte moves, the rest 4. The moves write from the data-path source register (0xDB) to the context RAM through pointer registers 12 and 8 (the shared routine's moves are `0xDB -> destination 12` and `0xDB -> destination 8`): by the form read, they are writes into the RAM, not reads out of it. That reading of direction rests on the register-move form and is inferred.
- That list is not on the path the kernel starts. The vector 8 entry tests four flags (0x40C to 0x413); when any is set it takes the long path (0x42C, through the list, then the tail at 0x4FB); when none is set it jumps from 0x42A straight to 0x4FB. Starting at 0x4FC skips both.
- The same register-index pattern shows two shorter writes in the vector 4 entry (the load phase, 0x36B): index 0x40 at 0x3E6 and a block write at 0x3F1 (pointer register 14 = 0x0050). The 0x0050 is a mode, not a count: one word is moved after it.

Graded answer to the question (are the table base, count and offset registers saved and restored per context by the microcode):

- Not saved by the routine the kernel starts (0x4FC to 0x530): established that it holds no host-address-generator register index and no loop over a context RAM. The 26 register values it sends are sourced from registers the instruction set does not yet name, so a host-address-generator value among them cannot be excluded by index; the shapes do not fit the slot registers (the slot state would be 20 words: five 8-byte bases, five counts, five offsets, in three groups, and nothing sends them in those groups). Grade: not saved by the kernel-started path, high confidence, not proven for the unnamed sources.
- Restored (written back) from the data stream on the long path of vector 8, including the table bases, counts and offsets: inferred from the move direction above. What starts that path, and where its data comes from, is not decoded; the kernel does not trace it (its 63-word image has no slot words and the load phase at vector 4 does not write them). Reading the four flag tests as DMA-in-progress conditions makes the long path a DMA-in-flight switch handler, with an ordinary switch (HQ idle) taking the short path. Grade: inferred, medium; settled by decoding what sets the four flags.
- Net for the table registers: the kernel-started switch neither saves nor rewrites them (established); the microcode has a restore of them for an in-flight DMA (inferred); so for a plain switch they behave as board-global registers and two clients that program the same slot do overwrite each other, which was the unsettled case in the earlier text.

Not run: execution of the microcode, or a board read of `HQ3_HAG_CTX` across a switch. In all sixteen members of the 6.5.13f `mgras.a`, the only store of a microcode start address to the board's start register (board base plus 0x130500) is in `MgrasCtxsw`: `addiu t0, 0x4fc` at 0x7a94 [0x7c3c], `sw` at 0x7a9c [0x7c40]. (The 0xa530 given in the second pass is the same store as a file offset; `.text` starts at file offset 0x2a9c.) Nothing in the kernel starts vector 8 (0x40C) or any other entry.
- Table registers are written only by the kernel, through the privileged command window (board base plus 0x130400), as command words of the form register number shifted left 8 or'd with a width word (`MgrasInstallTxTbl_Kern` 0x1f0 to 0x288, `MgrasResetTxTbl_Kern` 0x2dc to 0x320 in `mgras_dma.o`). The `0x820($s0)` and `0x830($s0)` operands in `MgrasPcxSwap` (0x417c to 0x4df8) are fields of a software record, not register writes. A user FIFO cannot program them: the command-FIFO privilege violation interrupt (`MgrasGeneralInterrupt`, bit 14) exists for that.
- The switch-time hardware touch is slot 2 only (`MgrasPcxSwap` calls `MgrasResetTxTbl_Kern` with slot 2 at 0x4854 [0x4778]). Slot 0 is not rewritten, saved or restored by any kernel routine on a switch, a request, a release or a close (see above).
- The load phase cannot restore them. Every call of the shared register-move routine (0x3FD) in the image is inside 0x455 to 0x4F2, the long path of the save entry. The load (vector 4, 0x36B to 0x3FC) writes only register index 0x40 (0x3E5 to 0x3E7) and a block under mode 0x50 (0x3F1 to 0x3F2). The 63-word image the kernel feeds it carries no table word (above). So whatever the long list does, the incoming context is not given a table base by the load.
- The register set the short save sends to the geometry engine (0x4FC to 0x522, sources r1 to r24, three of them 64-bit sends from r22 to r24 at 0x51C to 0x51E) is the mirror of the set the load fills from the stream (0x3AC to 0x3CD). That pair is the host-interface working state that goes into the context's geometry-engine memory slot (0x17C7 words apart); a slot record has no room shown for twenty table words, and three 64-bit sends are fewer than the five bases.
- The load (0x375 to 0x37B) carries the same four-flag test as the save (0x40C to 0x413), each leading to a variant path. So the flags are a common condition tested by both phases, which fits an in-flight host transfer (inferred, not decoded).

Graded answer for IRIX 6.5.13f and 6.5.30m on an Octane with IMPACT graphics:

- Are the table bases, counts and offsets (and so the server's slot 0) part of what a switch saves and restores: no. Established for the kernel (single start at 0x4FC, no kernel writer on a switch, no table word in the image) and for the load (no register-index writes). Inferred, high confidence, for the save: the short entry sends only the working-register set that mirrors the load, and the one full list of table registers is on a path nothing starts. Unknown: the semantics of the register-move forms (no instruction-set document), and whether the context RAMs at 0x50200 and 0x50300 keep a copy by hardware outside the microcode (the header names them; no kernel routine was found that reads them by name, a search by address window only, not exhaustive).
- Is the raster-interface state per context: the raster registers are not saved by the board (`HQ3.h`, context management; image words 18 to 39 are the X server's screen-wide registers re-sent from its shadow, none from a read-back). The context RAM named for the raster interface (0x50200) has no reader found in the 6.5.13f `mgras.a` (address-window search, not exhaustive) and no index writes in the load. The claim that the host-address-generator and raster-interface context RAMs hold these registers in each context's slot record has no support in the kernel, the image or the microcode entries the kernel uses.
- Net: after a GL client programs slot 0 and releases it, the next server copy through slot 0 uses the freed table, on 6.5.13f and 6.5.30m. A switch back to the server does not restore it. This agrees with the second pass and entry 20; the first answer (board-global, the server installs slot 0 once, neither kernel switch nor save touches them) stands with one correction: the kernel does touch slot 2 at a switch, and "the save does not touch them" is established for the entry the kernel starts, not for the microcode as a whole.

What would settle the remainder on hardware: read registers 0x20 to 0x28 and `HQ3_HAG_CTX` before and after a switch between two clients that program slot 0 differently, then run one server copy after the second client exits. That needs an Octane with IMPACT graphics online and the owner's agreement under the physical-test rule; no proposal has been made. Without hardware: name the register numbers 0xC0 to 0xDF and the move destinations in the instruction set (the vendor's instruction exerciser in the diagnostics is the likeliest published source), then re-decode 0x452 to 0x4F3 and 0x4FC to 0x522.

### 20. Who programs the display server's table slot, and whether it ever restores it

Question: after a GL client has reprogrammed a table slot the display server also uses (entries 16 and 19), how does the server get its mapping back. Builds: the X driver `impactsr.so` of 6.5.13f (`ed8a8191...`) and 6.5.30m (`ff37f8cf...`), and `libGLcore.so` of both (`b1fef785...`, `7030d7b1...`). The server program `Xsgi` itself holds no table request: neither build's `Xsgi` contains the request's command constant. Addresses are 6.5.13f first, 6.5.30m in brackets. Read from the machine words, not executed.

Command map, from the kernel's ioctl dispatcher in `mgras.o` (a small interpreter over the compare tree, checked against the handler blocks): table requests are 0x6d67000b (single), 0x6d67000d (multi), 0x6d67000e (replace), 0x6d67000f (append) and 0x6d67001f (release); 0x6d67001e is the texture share call. 0x6d670063, used by the copy and draw routines, reaches a branch that only logs a kernel message and changes no table. A request's first word is a flag set (bit 2 list given, bit 3 flush, bits 0 and 1 release), the second the slot.

Established. The server issues the single request (0x0b) from these places and no others in either build:

- `mgrasKernInit` (0x5e50f850 [0x15b80e0]): once, at screen start, flags 0xC, slot 0, one 16 KiB region of its own (word 0x4000). It is reached only from `mgrasInit` (call at 0x5e510a18 [0x15b8650]), the screen initialiser. This is the slot-0 install the trace shows (count 4 is 16 KiB in 4 KiB pages).
- `mgrasCloseScreen` (0x5e506364 [0x15b7660], request at 0x5e506478 [0x15b777c]): flags 3, slot 0, then frees the 16 KiB region. This is the only release of slot 0.
- Host pixel transfers install their own slot per call and release it after: `mgrasDrawPixels` (0x5e526bbc [0x1697a20], requests at 0x5e5272b0, 0x5e527aec, 0x5e527ba8, 0x5e527c18 [0x1698090, 0x169888c, 0x1698934, 0x1698990]), `mgrasReadFBBlock` (0x5e5166c4 [0x166a2e0]) and `mgrasWriteFBSubBlock` (0x5e515bfc [0x1669810], 0x5e51603c [0x1669c50]) with slot 3 and flags 0xC then 3 where the slot field was decoded (DrawPixels, ReadFBBlock); `mgrasReadPixels` (0x5e523390 [0x16aa680], 0x5e524644 and 0x5e524718) builds the same request from a global copy and its slot field was not decoded. None of these touches slot 0.
- Screen-to-screen copies and weaves make no table request. `mgrasCopyPixels` (0x5e4fe310 [0x16af3c0]) writes the host-address-generator registers and the start word itself through the command window, on two paths: start word 0xB9 (0x5e4fe8cc to 0x5e4fe8d4, the value read from a constant table at 0x5e546980) and 0xB1 (0x5e4fedc8 to 0x5e4fedd4, built as 0x2C400381 shifted left ten). [0x16af970 and 0x16afe64.] Its only ioctl is the 0x63 log call. So the copy path runs on whatever mapping slot 0 holds when it kicks. It has no flag recording that slot 0 is the server's and no callback that reinstalls it: no other site in either build writes slot 0, and no expose, restore or context-regain handler leads to `mgrasKernInit`.

So the answer is none of the three candidates. The server programs slot 0 once at screen start and releases it at screen close, and assumes it stays.

The GL library side. `__glMgr_LockSingleDMAPool` (0x0dab29e0 [0x0d9c2560]) and `__glMgr_UnlockSingleDMAPool` (0x0dab2b10 [0x0d9c26a0]) issue the same request with a pool index as the slot: lock with flags 0xD, unlock with flags 3. The library keeps its own cache of the locked range per pool at context offset 0x7D00 plus 16 per pool and skips the request when the new buffer lies inside the range already locked (0x0dab2a0c to 0x0dab2a5c), so repeated reads reuse one install. It has no knowledge of the server's use of the slot.

What the kernel does with that (entry 19): the lock rewrites the board's base, count and offset registers; the unlock frees the kernel's table and the pinned pages and writes only the invalidate register and sync words, leaving base and count pointing at the freed table.

Whether a server copy can then run against the freed table: yes, in the code. After a GL client has installed and released slot 0, the next `mgrasCopyPixels` kick in the server uses the registers as the client left them, with no reinstall and no check, on both builds. With the registers board-global (entry 19 and the microcode read), real hardware would perform that copy's transfers through whatever the freed table's memory holds, stale or reused. The picture the server draws after the client exits is therefore not guaranteed by any code in the server; a wrong or empty screen in that case follows from the code. This depends on the copy's start word selecting slot 0, which the trace states and these routines do not show (the 0xB9 and 0xB1 words' table select bits were not decoded), and on the GL client using slot 0, which the call-site reading below settles for the held library build.

The pool index at the library's call sites, read in the held `libGLcore.so` (`usr/gfx/arch/IP28GR432/libGLcore.so`, sha256 `eca0027567a5ae88...5c2e`, the build the file checklist takes from the 6.5.0 distribution; not the 6.5.13f and 6.5.30m builds above, which this root does not hold, so their call sites are unread). Addresses are in that build. `__glMgr_LockSingleDMAPool` (0xdade018) stores its sixth argument (a5) as the request's second word (0xdade0bc) next to the flags 0xD (0xdade0b8) and sends request 0x6d67000b (0xdade0f0), so the pool index is the slot (established; the same function indexes its cache at context offset 0x7D00 plus 16 per pool, 0xdade054). Sixteen call sites, found by every load of the function's global-offset-table slot in the text:

- Slot 3 always: `mgrTM_DoTexLoad` (0xdabfc7c, 0xdabfd14), `mgrTM_DoTexRead` (0xdac08fc, 0xdac099c, 0xdac1318, 0xdac13b4), `__glMgrim_GetHistogramEXT` (0xdacb514) and `__glMgrim_GetMinmaxEXT` (0xdacd314). `retools/tools/hostfacts.py` resolves the register to 3 at every one of these sites; the plain sets are `addiu` at 0xdabfc60, 0xdac08e4, 0xdacb500 and 0xdacd300.
- Slot 0 always: `mgrTM_SR_TexRead` (0xdac24d4, 0xdac259c; the register is zeroed at 0xdac24a8) and `__glMgrSlowCopyPixels` (0xda85ea8, 0xda85f50; its pool register is zeroed at 0xda85e7c and written nowhere else in the routine).
- Either, by a flag byte: `__glMgrDoReadPixels` (0xda866d0, 0xda86768) uses slot 3 when the byte at context offset 0x7c7c (read at 0xda865d4) is zero and slot 0 otherwise (the register is zeroed at 0xda865e0 and set to 3 at 0xda869f8). The only other access to that displacement anywhere in the library's text is a clear in `__glMgrInitPixels` (0xdaf2ab4), so no store that names the offset sets it; a store through a computed base would not show in that search (unknown). `__glMgrSendPixels` (0xda84f98, 0xda85048) keeps its slot at stack offset 0xf0: slot 3 when the byte at its argument record's offset 0xc0 (read at 0xda84334) is zero, slot 0 otherwise (0xda84340 and 0xda84e0c). That byte is set by `__glMgrSlowCopyPixels` at 0xda85e68 to the result of a size product against 0x8000, and `__glMgr_UseDMAForRead` and `__glMgr_UseDMAForWrite` return 1 at once when it is nonzero (0xdaddf80 and 0xdadddf4), so it reads as a use-DMA flag (inferred).

So in this build the GL library does use slot 0, the slot the display server installs once and assumes: always for the slow copy path and the `mgrTM_SR_TexRead` texture read, and for a pixel send or read whose flag byte selects it. A client's lock and unlock of slot 0 therefore rewrites and then frees the table the server's later screen-to-screen copies run against, which is the case entry 20 reasoned about from the code above (established for this build; whether real hardware keeps one table for both is the board-global register question of entries 19 and 16, which this reading does not touch).

Still open: which table each start word (0xB9, 0xB1) selects. Settling test: decode the start word's select bits in the host-address-generator microcode. The 6.5.13f and 6.5.30m call sites are unread; the same eight-routine search on those builds would confirm the slot choices carry over.

### 21. Raster arithmetic

Question: the rounding, tie and reduction rules of the raster path. [devices/mgras/raster-reference.md](../devices/mgras/raster-reference.md) tabulates what is known per stage.

Read: the shipped standalone diagnostic (`ide`, IP30 build from the IRIX 6.4 disc, sha256 `43237354b4ad84ab9a8328d8b2109b1fccd115c9b00d8f6b5e0f8a10e747659e`), by static reading only. Results are on [devices/mgras/ide-raster-tests.md](../devices/mgras/ide-raster-tests.md). Established there: the tests compare a read-back image with stored expected tables (no model of the board is computed), and the stored "CRC" values are plain 32-bit sums of those tables (checked for the four colour triangles, the lines table and the stipple table). Settled from the stored colour-triangle images: an exact tie on a right edge is excluded; colour is stored as a dithered value with a fixed 4 by 4 threshold pattern and no bias (intervals tabulated, matrix not recovered); the setup bias 49151.5 and the colour start scale `0xFFF000` appear in the diagnostic's own host setup. The one-TRAM revision B render checksum is `0xbdfc48fc`, not the `0x0bdf48fc` recorded earlier.

Still open, with what would settle each:

- Setup snap in the geometry engine's ALU (host add is double then single in the FPU's mode). Operand trace of `trigeom`, or a vertex at n + 1/512.
- Left, top and bottom edge ties; span end rules for points and aliased lines. Two triangles sharing an edge through a pixel centre; the `mg_lines` table needs its endpoints decoded (the 17 by 14 table at data offset `0x1800` is in hand).
- Depth rounding, floating Z, stencil saturation, alpha-test width, blend arithmetic and which chip blends, logic-op width beyond the 24-bit compare mask. - Texture: iterator widths, divide precision, LOD arithmetic, filter weights. Texture tests (`mg_tex_load`, `mg_tex_poly`) have stored tables from data offset `0x46d8` not yet decoded.
- Which pixel types the dither applies to, and whether the test or the store enables it.

## Video and sync hooks: open questions and proposals

Added with [video and sync hooks](../devices/mgras/video-sync.md). Each entry names the unknown, the evidence tried and the
smallest test. None needs anyone contacted; the physical ones wait for the owner's agreement under the repository's rule for
bringing the user's systems online.

1. **Which writer of the board configuration word (`0x072408`) the board follows for genlock.** Unknown: the kernel's
   `MgrasSetGenlock` writes `0x64000000` or `0x60000000` by its sync-output argument; the diagnostic's helper writes
   `0x20000000` or `0x24000000` by its genlock argument. Evidence tried: both routines read in full, no read-back of the
   word exists in either, and the word's top byte is read for board identity, so a read cannot show the written bits. Smallest
   test (physical, IMPACT board; James's Octane2 is a VPro, so none is available to us): with a scope on the genlock BNC and a known reference, send one `MGRAS_SET_GENLOCK` request
   (`0x6d670014`) with each of the four combinations of its two words and record the sync output and whether the screen locks.
   Four requests, no register reads.
2. **Whether the VC3 display-control bits 5 and 6 have any status counterpart.** Unknown. Evidence tried: the kernel never
   reads index `0x1e`; the diagnostic reads it back only to print the bits it wrote. Smallest test (physical, IMPACT only, not available on James's systems): with the
   reference connected and then removed, read VC3 index `0x1e` and `0x1f` (index write to `0x072008`, 16-bit read at `0x0720b0`;
   neither has read side effects in any code seen) and see whether any bit other than the written ones changes.
3. **The video-option bit.** The kernel reads bit 7 of the byte at `0x071708` clear as "option attached"; the diagnostic's
   `RA Board version` routine (`ide` `0x20849f9c`) tests bit 6 for its "video board not installed" message. Both cannot name
   the same line unless bit 6 is also the top bit of the RA revision field. Evidence tried: both code paths read; no captured
   board value of the byte is held. Smallest test (physical, read-only, IMPACT only, not available on James's systems): one byte read at `0x071708` with no
   option, recorded verbatim. Reading the kernel and diagnostic again gave a consistent reading, bit 6 and bit 7 as separate absent lines (video board and option connector), recorded as inferred. A plan naming the register's side effects is needed first: none are known, it is a plain
   status byte in the DCB device window the kernel reads at every attach.
4. **The DAC signature registers and the expected words.** Settled in part by the data sheet (see the video-sync page, section 4.3): the
   algorithm, inputs, control bits and readout are decoded. Still unknown: the gate polarity after the NAND in the data sheet's
   figure, the reset state and the exact displayed frame behind each of the 42 expected words, so the stored words are not
   reproduced. Settled without hardware by emulating the diagnostic's generated expectation routine (`0x2084dc80`) for the
   walking-one colours and comparing with the analyzer model. A physical read is not available (James's Octane2 is VPro).

## Cut commands and taking the board back (2026-11-27)

- **What the board does with a command that stops short.** Numeric packets are single 64-bit stores, so only a staged-then-execute sequence can be cut; a GL command with a byte-count header can be cut inside its payload. No shipped code or document says whether the board waits, times out or takes the next words as payload ([hq4-host-interface.md](../software/kernel/hq4-host-interface.md#a-command-cut-short)). Routes tried: the IP30 exit, suspend, DDRN-destroy (which context-switches to the default context when the running one is destroyed), timeout and context-switch paths, the 6.5.7 text port library. Next: write a decoder for the HQ4 microcode image and read its command-header handler (software now); a model of the board's input logic (hardware only).

These tests give the frames-per-second rates whilst spinning various 3D Inventor objects. Some of the models are my own, created over the years; others are from various SGI demos, eg. the 'Underwater Camera' and 'Huge Engine Model'.

NOTE: The frame rate figures given here are for single-buffered tests, ie. no attempt is made to synchronise the drawing of the 3D image with the display refresh of the monitor. Thus, a system's graphics hardware renders a model as quickly as possible, which means observed frame rates will usually be an obscure fraction of the monitor refresh rate, but can also be many times the refresh rate if a particular graphics system is sufficiently powerful or if the model is simple.

By contrast, double-buffered tests involve waiting for a monitor refresh event to synchronise the drawing of the object with the frame-by-frame display of pixel data on the screen. Thus, frame rates for double-buffered tests can never be more than the monitor refresh rate, are usually an integer divisor of the monitor rate, and usually do not represent the maximum capabilities of a graphics system. I present results of both types of test in order to offer as broad a range of information as possible, and also to show very clearly how different these two types of test can be. For full details on this issue, see my page on The Effects of Double-Buffering on Animation Frame Rates. I dedicate all effort to single-buffered tests now though since they are far more meaningful.


MAJOR UPDATE (29/Jan/2009): in recent weeks I took a closer look at all these results, after learning some new things about SGI gfx hardware and studying the CPU usage of various configurations. Firstly, I finally found out how to force an SGI to run any application in single-buffer mode, including any Performer application, namely by setting the environment variable, "DECOUPLE_SWAPBUF" to 'y'. Even though ivview has a menu option to use single buffer mode, that's just the rendering method within the Inventor application rather than the raw hardware setting. Using the above environment variable turns on true single buffer mode, giving more accurate results. Often this does not make too much of a difference, but it can do in some cases. Note however the setting is not applicable to O2 systems as it induces screen corruption in 3D windows such as Inventor.

Next, by using osview to monitor CPU usage, it is very clear that a great many of the SGI systems tested here are CPU-bound when running these tests. That is, the results are limited by the CPU speed, revealed by osview showing the CPU running at or near 100% usage. This is made worse by the fact that Inventor only uses one CPU to run ivview, so on any multi-CPU system the potential of all the other CPUs is wasted. Whether or not a system will be CPU-bound for any individual test depends on the window size, the precise graphics configuration, the nature of the 3D model, the application/libraries used to render the model (eg. Performer, Inventor, Maya, Alias), and to what extent the gfx hardware being used is applicable or not for the particular render mode being tested, eg. textured vs. wireframe.

These factors all mean that the results here should be taken with a major pinch of salt. For example, the Huge Engine Model 'MW' (Maximum Window) test gives 10.76 fps on my Fuel 900MHz V12 (with 94% CPU usage), but if I load the model into perfly instead then the frame rate rockets up to 68 fps and only 78% CPU usage! (or 88fps with textures turned off, giving almost 10M tris/sec, more inline with what one expect V12 to be able to do, at least on a single-CPU system anyway). In other words, using ivview to display the model means the bottleneck is often the main CPU, not the gfx, and note that the ivview numbers show Inventor is particularly slow at coping with textures.

The difference can be even larger on any multi-CPU system since perfly can utilise all available CPU resources. Testing various systems and models has shown that in many cases using a more optimised application such as perfly can give absolute performance results (triangles/sec I mean) that are an order of magnitude faster (or more) than the data shown here. This is especially true of high-end systems, any system with fast graphics (eg. desktop VPro) or tests that have their own inherant bottlenecks (eg. large landscape models).

I can only assume Inventor's internals must involve a rather top-heavy way of handling the 3D data, perhaps the high-level scene graph description is to blame. perfly accesses the graphics hardware more directly using a more optimised scene graph and so is much faster. Where things get complicated is when, for a particular test, a system may be CPU-bound with a large size window but gfx bound for a small size window, or it may be CPU bound in one rendering mode but gfx bound in another mode. Or a combination of these possibilities. Onyx2 reveals this strongly, with good results for shaded mode, but slow results for wireframe (CPU usage maxed out for wireframe, ie. the CPU is the bottleneck); on the other hand, having 2 RMs vs. 4 RMs can muddle this up, ie. MW tests may or may not be CPU or gfx bound depending on the test, CPU, gfx mode, model complexity, etc.

For example, consider the chromeskins results for two of the Onyx2 systems:

                                             MW     MW/SH   MW/W     SW      SW/SH   SW/W

When the window is large, pixel fill is more important when textures are turned on, so the 4RM system is faster (probably caused by Inventor's poor handling of texture data). With textures off, the gfx hardware can go much faster (because of how poorly Inventor handles textures), so performance is now limited more by CPU speed - this is why the MW/SH and SW/SH results are almost the same for the R10K/250 system, but quite different for the R12K/400 system, ie. the /SH tests on the R12K/400 system are less dependent on CPU speed. But in wireframe mode, the bottleneck may be a combination of both factors: the R12K/400 eases any CPU bottleneck which might be present in the R10K/250 system, but its smaller number of RMs may cancel out the benefit of using a faster CPU, in both cases perhaps made worse by the way Inventor draws lines.

So, what to conclude? Well, these test results always were supposed to be 'real-world' tests, an example of what real work might involve for ordinary users, but to be fair to SGI's systems, it's unlikely users of mid-range and high-end systems would be using Inventor that much. As such, the data on this page is gravely understating how fast SGIs can be.

SGI's preferred library/API suite for obtaing maximum performance is IRIS Performer; most major 3D applications aimed at SGI high-end systems use Performer, eg. Vega/MultiGen. Alas, at the moment I don't know how to use perfly to display a model in exactly the way I want for a repeatable test, but I shall look into this. For now, it is safe to assume that whatever numbers you see here, in reality SGIs are capable of operating at significantly higher performance levels.

The objects I've used for these tests vary in their nature, but they do share one aspect in common: they're not 'perfect' objects, ie. they're often inefficient in their definition. This is entirely deliberate, because in the real world that is exactly how many 3D object files are constructed, eg. a landscape data set may have a huge number of triangles wastefully used to represent a flat area, but someone working with the model might not be allowed to alter it, or may not know how even if they could. Thus, although I always use the command 'ivview -p' to run these tests, I do not use ivview's object-optimisation options. Sometimes of course, it's possible to use software such as Optimizer to improve performance, but I don't deal with such issues here.

For each object, a brief description, the number of polygons it contains and a link to a screenshot are provided. Feel free to browse the screenshots page, which has most of the object models available for download.

Caveats:

  • Some results may seem strangely out of order; this is because the frame rates can be greatly affected by exactly how a model is spun. The data for the angus, engine, stars and spacestation models shows this, but examples can be found in almost every table. With hindsight, it would have been better to write some kind of testing program that loaded each model and either spun it in a predefined way, or simply calculated how long it took to draw the default view in each mode a certain number of times. Over time, I'll retest some of the configs where the numbers don't seem right. The landscape tests are a good example - the model is supposed to be rotated verticaly face-on before being spun, in order to maximise the fill demand, but if it's simply spun edge-on with the default view, then the results come out too high. This is why, in the tables for the ss models, an R12K/300 SE appears to be quicker than an R12K/400 SE.

  • Monitor settings are if possible always 1280x1024 at 60Hz with 32+32 or the nearest-best (early results were often done with 72Hz displays, which may have slightly reduced the numbers for some O2 configs); exceptions are the Onyx2 R10K/195 results which were run at 60Hz 1920x1200 resolution, and the Onyx2 R10K/250 tests I ran which were done at 1280x1024_60, though the actual display I was using was 3840x1024. In addition, some R12K/400 Octane V6 results were done at 1280x720, which unfortunately means the results can make V6 look as good or better than V12, when in fact V12 is definitely faster, ie. at the lower res, V6 is dealing with a 30% smaller fill area. I will rerun the tests at 1280x1024_60 when I am able (it doesn't matter so much if the refresh is 60 instead of 72 though since the tests are single buffered anyway).

  • The results given for R10K/195 Onyx2 used just one CPU and one RasterManager (RM7); thus, they should not be used to judge the maximum performance of Onyx2 which is massively higher than the figures given here. My thanks to Michael Tiemann for supplying the Onyx2 data. Compare Michael's results to my own which use IR2E and R10K/250.

  • Ranking rationale: Each test consists of several sub tests. A system X is ranked better than system Y if X achieves better results for a majority of the sub-tests, eg. I2 R4400SC/250 2MB XL24 is ranked better than Indy R4400SC/200 1MB XL24 for the underwater camera model because it beats the Indy for 4 out of the 6 sub-tests. For those cases where there is a tie, then the system with the better max-window (MW) score is ranked first. If two systems tie on one sub-test but not others, then that sub-test is ignored and the judging rationale is repeated on the remaining tests. This ranking method is most evident when looking at texturing results for systems with no hardware texture mapping support, eg. look how far up the table R10K SolidIMPACT reaches despite it's low texture result - it's because the shaded/wireframe figures are better than the systems lower down, ie. for 4 out of the 6 tests. This allows systems which would be good for certain tasks to remain higher above the table and easily visible, rather than being placed way down the table just because of the results of one particular test. However, it does mean that sometimes it is possible to place a system's results in more than one possible position, depending on whether one compares results going top-down or bottom-up through the table. In general, I compare results bottom-up.

  • The 2GE Indigo2 XZ outperforms the 4GE Indigo2 Elan for the textured tests probably because of issues concerning graphics context switches (the CPU must do the texturing, which interferes with the smooth flow of data). For shaded/wireframe tasks, the 4GE system is faster as expected.

  • For some of the models, the bottleneck in the rendering process is the rate at which the main CPU can supply data to the graphics pipe. This is especially important where high-end systems are concerned, both old and new, eg. examine the Test B results for POWER Series RE 1RM: note how, compared to using R3000/33, the frame rate first doubles, then triples, when using the faster R4000/100 and R4400/150 CPUs instead (respectively). Even more critical is that all these Inventor tests only use one main CPU. Thus, if one recompiled ivview to use more than one CPU, some systems could easily increase their performance by a huge margin.

  • Tests involving texture mapping only make use of a single texture usually operating in environment mapping mode (the exception is the Earth model which employs a static texture), ie. these are not representative of tasks where multiple different and size-variant textures may be used in a scene, such as urban modelling. This means such tests here cannot convey how SGIs vary in their texture memory capacity or texture data loading speed. Instead they just show how much of a difference it makes to have any hardware acceleration for texture mapping at all. A more relevant test in terms of capacity and loading speed would be, for example, a large DOOM WAD level in Inventor format which has a different texture for every surface; this might need more than 4MB TRAM and thus would not fit into the TRAM of IMPACT or RM4 RE2, but would be no problem for VPro, RM5 RE2 or any IRx system. Or a more extreme test would be a volumetric texel dataset such as a CT or GIS model.

A note about the V12 results compared to V6: from what I can gather, only the power of the GE subsystem was increased from V6/8 to V10/12. Thus, please make careful note of the following table when looking at the V6 and V12 numbers:

                     CAD-oriented, fewer    GIS, imaging, heavy texture
                     hw features, not so    oriented, complex animation,
                     much VRAM or TRAM.     more features, dual-head, etc.

Old Series VPro         V6 (32MB RAM)               V8 (128MB RAM)
Original GE speed

New Series VPro         V10 (32MB RAM)              V12 (128MB RAM)
2X Faster GE speed

Some observations which result from the above:

  • For fill-limited tasks, V12 will not be that much faster than V6 or V8 at the same resolution. There will be some speedup, but not much. This is clear in tests such as full-screen-textured HugeEngineModel.

  • For geometry-limited tasks, V12 will be much faster, up to 100% faster, than V6 or V8 at the same resolution. This is very clear in the stars3 and stars4 results, which (taking the screen resolution difference into account) show a perfect doubling of speed from V6 to V12.

  • For other tasks, the speedup from V6 to V12 varies since both fill and geometry can matter to different degrees. Thus, for shaded tasks, there is a speedup, and a better speedup than for textured. For wireframe, there is a significant speedup (typically 50%) because fill rate is less important for wireframe, though it does still matter when a model is large.

So if you're a V6 user, do you need V10? If you're a V8 user, do you need V12? Well, it depends on what you're doing. This is definitely a case of try before you buy. One should also analyse main CPU issues before considering a gfx upgrade - maybe the main CPU is the bottleneck. What does osview say when an application is active? The models tested here don't cause much in the way of dynamic data transfer between main RAM and the graphic board, so more complex applications may behave differently, eg. Octane MXI should perform much better than Indigo2 MaxIMPACT for a RAM intensive 3D task.

# Open questions and what the shipped software settles

The hardware headers mark what they do not know with "not known", "unknown" or an `UNKNOWN` label. This page is the ledger for those marks. Each entry says whether the shipped software settled it, the evidence, and for what is still open, what would settle it.

Grades are established, secondary, inferred or unknown; the legend is in [AGENTS.md section 7](../AGENTS.md#7-published-documents). None of these is a measurement of the silicon. Binary evidence is cited by object and text offset in the 6.5.22 kernel graphics objects (`mgras.o`, `mgras_init.o`, `mgras_mco.o`). The diagnostics are the 6.5.7 standalone graphics diagnostics and their option-board command registry.

This pass covered the host interface, the board-level words and the multi-channel option, and later passes (entries 6 to 14) took more of the open marks. It did not examine the texture engine marks, the geometry-engine operation codes or the vertex-path marks; they are listed under "Still open" with the evidence that would settle them.

## Settled in this pass

### 1. Multi-channel option register map

Question: "what the option board's index values control" (board header, display control bus device 11). Settled. The kernel object that loads the option (`mgras_mco.o`: probe at text offset 0x0, FPGA load 0x30c, the two DAC loaders 0x590 and 0x96c, timing chip 0xb24, device 11 timing word 0x11a0, control registers 0x127c, ADV7162 register pointer 0x1328) uses a byte index port and a byte data port, and the index is a bank in the high nibble and a port in the low:

| Index | Target | Grade |
|---|---|---|
| 0x2n, 0x3n | ADV7162 true-colour DACs, channels 1 and 2 | established |
| 0x0n, 0x1n | ADV473-class overlay-palette DACs, channels 3 and 4 | established |
| 0x80, 0x90, 0xA0 | board control registers 1, 2, 3 | established |

The bank bases come from a five-entry per-channel table in the object's initialised data (0, 0x20, 0x30, 0, 0x10 for channels 0 to 4). The part names come from the loader routine names and the option's diagnostic command list (the registry lists 7162 and 473 palette tests). Ports on an ADV7162 channel: +0 is a 10-bit register pointer written as two bytes; +1 the palette data (256 entries of six bytes, each colour's high 8 bits then its low 2 bits); +2 the data port of the register the pointer selects; +3 a port the probe writes 3, 2 and a table byte to (role unknown; test: read the 7162 loader's call that passes 3 to the register-pointer helper and its other port +3 writes in `mgras_mco.o`, then compare the three values with the ADV7162 data sheet's port map, which is not held and must come through the Library acquisition tooling; or capture the board's bus traffic around a write to +3 and a read of +3 and see whether the byte echoes). Reading register 3 returns 0x79 on a healthy part (the kernel compares), so register 3 is the identification register. Ports on an ADV473-class channel (graded: +0 and +1 established, re-read this pass in the option's 473 loader and 473 gamma loader, which write the palette address to port 0 and then three bytes per entry to port 1, one byte each from three 256-entry colour tables; +6 is established as a write of one value from the caller's first word at index base + 6, re-read in the 473 loader's machine words, and its role as the command register is inferred; `MGRAS_DECODE.h` now carries these ports as bank-relative port numbers): +0 palette write address, +1 palette data (three bytes per entry), +6 command; +2 is inferred to be the pixel read mask because the display server writes it (0 or 0xFF) in its blanking sequence and the family's register order puts the mask there.

The option also has an FPGA configuration path (data byte at display-bus register select 0, control and status at 1) and its own timing chip (select 4 picks a register, select 5 is its 16-bit data, select 7 the auto-incrementing timing RAM). The FPGA load checks status bits 2:0 as 000 after the first control write (0xFE), 110 after the second (0x01) and after every data byte, and bits 1:0 both set after all 0xF688 bytes and 20 zero padding bytes. The board-ID probe at the start of the same object has two shapes, one per CPU board family, and both readings that have been written here were right for some build and wrong as a general statement. See "Board-ID probe, per build" below; do not state the probe without naming the build family.

### 2. Blanking mask register

Question: "which DAC register the display server's blanking writes reach". The display server writes register pointer 4 (bytes 0x04, 0x00) of the same ADV7162 and then 0x0000 to blank or 0xFFFF to restore. Established: it is register 4 of the ADV7162, written 16 bits wide. Inferred: it is the pixel read mask (the effect is to mask every pixel). No ADV7162 datasheet is in the Library to check the register number against.

### 3. Host interface error causes

Question: the flag register's causes beyond the ones named. Settled for four. The kernel's general interrupt handler (`mgras.o`, text offset 0x8378) tests the group 0xE200 and, in order, prints a microcode error (bit 9), a DMA address range error (bit 13), a command-FIFO privilege violation (bit 14) and a DMA access or stack overflow (bit 15), clearing each through the interrupt-enable clear register. The messages are matched to bits by the handler's string-pointer offsets, which land on consecutive strings in the object's table in the same order; the interrupt enable the kernel programs at boot (`MgrasInitialize`, right after `MgrasInitHQ`), 0x4400E200, contains exactly this group plus the two FIFO high-level bits. The same handler also uses bit 16 (sync complete), bit 19 (context saved), bit 6 (context loaded) and bit 10 (buffer swap), which agree with the headers.

Changed: the old `error` reading of bit 8 is dropped from the header, and the matching `error` field and flag macro are removed from `HQ3_DECODE.h` and `HQ3.h`, so bit 8 is now unplaced everywhere. The handler never tests bit 8, and the diagnostics' walk of the flag registers masks 25 bits (0x1FFFFFF), so there are 25 flag bits in all.

Still unknown: what raises flag bit 20. The kernel enables it at start-up (the flag-enable value 0x11000F is bits 3:0, 16 and 20). The buffer-swap path (`mgras.o` text offset 0x402c) reads bit 20 from the flag register, clears it and flushes the command FIFO. Reading how the microcode raises it, from the host interface microcode (`hq3.u`), would settle it.

### 4. Host interface values the kernel programs

Question: the headers listed watermark defaults "older notes recorded" and said the drivers program others. Established: `MgrasInitHQ` (`mgras_init.o` text offset 0xfac) writes configuration 0x7E8C (OR the caller's bits), GIO configuration 0x765B900F, command-FIFO high 0x20 (less twice a per-board count when that is positive) and low 0x14, delay 0x64; data-FIFO high 0x28, low 0x14, delay 0xFFF; bus-FIFO low 2, high 6, delay 0x8C; flag enable 0x11000F; and clears every cause and enable first. Its caller then writes the interrupt enable 0x4400E200. The information-gathering routine (`mgras_init.o` text offset 0x8a8) writes the configuration as 0x7E8D, the same value with bit 0 set. The standalone diagnostics program 40 and 20 with delay 100 for both command and data FIFOs and 8, 2, 100 for the bus FIFO. The two sets are now separate constants in `HQ3_DECODE.h`. The configuration register is 15 bits on this chip (the diagnostics test it with mask 0x7FFF; 0x3FFFF on the later host-interface part), so bits 14:9 of the init value are real state; their meaning is unknown, and a register description of the host interface or a write/read-back probe would settle it.

The GIO configuration value decodes against fields the headers already define (bits 3:0 and 12 set, bit 6 clear) and against the bus-master timing fields in `HQ3.h` (all set), which is consistent with those fields being real.

### 5. Board identification probe

The kernel's probe (`mgras_init.o`, text offset 0x770) accepts a board only if the first word has bits 6:0 equal to 0x10, bit 16 set, bit 17 clear and bits 31:18 equal to 1, and does not look at bits 15:7. The word the headers record, 0x00050190, passes. So the "revision" nibble at bits 7:4 is only partly checked (bits 6:4 must be 001, bit 7 is free), and bits 15:8 are not compared by the probe; the information-gathering routine later saves bits 15:8 as a one-byte board field. The headers' revision and product split stays inferred; the probe fixes only which bits are compared. A second board's identification word (another revision) would settle the split.

### 6. Framebuffer size register, top byte

Question: what the top byte of the DRB size register (pixel processor register 0x16E, traced as 0x90 under 6.5.22, per `PP1.h`) means. Settled in the sense that it is not a programmed setting. The kernel routine that writes the register (`MgrasSetRSSTiming`, `mgras_init.o` text offset 0x21b8 in the 6.5.30 object and 0x1fe8 in the 6.5 base object) builds the value in a register from the screen width and the raster-engine count: it replaces bits 1:0, 5:2, 7:6 and 9:8 in turn and clears bit 10. It starts from a word it loads from its own stack frame at offset 0 (`mgras_init.o` text offset 0x2280, 6.5.30; 0x2084, base), and nothing in the routine stores to that slot before the load: the only stores to the frame are the saved registers at offsets 8 and up, and the slot's address is never taken. So bits 31:11 of the written value are whatever an earlier call left on the stack, not a value the driver chose (inferred from the code; both objects have the same shape). The write is one 64-bit store into the board's command window at board base + 0x120400, the upper word a fixed command naming register 0x16E (command word 0x00196E04, read from the object's 8-byte constant table) and the lower word the value. The same routine then writes register 0x16D from a word in the timing table (offset 0x6c), with the command word 0x00196D04, also from the constant table.

Why this matters: the 0x90 the 6.5.22 trace shows is stable across the two boards traced, which fits a deterministic leftover from the preceding calls and does not need a hardware meaning. The standalone diagnostics and the boot-time info routine never set the top bits (the low words at 1024x768 are 0x31A for one raster engine and 0x25A for two, as `PP1.h` and `PP1_DECODE.h` record them, and re-reading the routine in the 6.5.0 kernel object (sha256 `8369b6d4a250d395123793a8dd339bfa0f158caa32cbf218fdb76a904725c9d7`) reproduces both from the width and the engine count: the two tile divisors 768 and 192, the engine count compared with 2, and the line-count field 3 unless the count is 2, when it is 2. The 0x90 top byte comes from the 6.5.22 trace, whose source was not re-read in this pass, so the full words 0x9000031A and 0x9000025A are not independently established; an earlier draft of this entry wrote 0x31E and 0x25E, which was a transcription error, since bit 2 set would make the 192-pixel tile count 7 where 1024 pixels give 6; corrected; the low bits are established from the routine), and the register still works. The headers now say the top bits are unprogrammed and unknown.

Still unknown: whether the pixel processor ignores bits 31:11 or latches them. Settling test: write the register with the top byte 0x00 and with 0x90 on a board and compare a full-screen fill and a read-back; or read the register on a board that has not had a driver run.

### 11. Command-stream tokens 0x096, 0x097, 0x0DA and 0x05F

Question: the meaning of the tokens the header lists as "meaning not known". Narrowed, not fully settled; the hardware meaning lives in the host-interface microcode, which I did not decode (the microcode object carries only a line table, no labels).

- 0x096 and 0x097 are a bracket (established, from the 6.5.0 graphics library's pixel read-back entry points): `glReadPixels`, the colour-table copy and the slow copy path send 0x096, run the read-back routine, then send 0x097. So 0x096 starts and 0x097 ends a pixel read-back, and glCopyPixels and glCopyTexImage2D use them because they read the framebuffer through the same routine. The header's note that they appear together in those calls is consistent.
- 0x0DA (established that it follows the wait for a board-to-host transfer): the DMA read-back helpers set up the transfer, spin on bit 1 of the user status register (0x70000), then send 0x0DA with no operand. The texture read path does the same after its own read transfer, and one path follows it with the raster state restore. Inferred: it releases the pipeline after a read transfer completes; what the microcode does with it is unknown.
- 0x05F carries one operand word that is not a GL enum, contrary to the earlier note (established): the texture manager sends it with operand 0 right after the texture mode is saved aside and before the texture-off token (0x00C); the enable and disable entry points send it with operand 0 or 0xE0100 in the same position when they switch texturing, and a GL enum goes out under other tokens (corrected: an earlier reading put the texture enum under 0x0A7, but in the 6.5.0 library, sha256 `eca0027567a5ae885ca2a996349ef838c07364c6c2e7535ba65076eb359a5c2e`, read with `retools/tools/hostfacts.py` and the disassembly of the disable entry point, 0x0A7 is sent only with the clip-plane enums 0x3000 to 0x3005, and 0x0A6 likewise from the enable entry point, which agrees with `HQ3.h`; established for that build; which token carries the texture enum was not read); and the routine named for sending the second texture-mode word sends it with 0.0 or plus or minus a float taken from the texture environment state. Inferred reading: 0x05F stores a second texture-mode word in the geometry engine, and the texture manager clears it while a load runs. The enable and disable association in the table comes from the first function that happens to send the token and is not its meaning.
- 0x0EB: not found as a command word in the 6.5.0 graphics library. The library's 0xEB is a different number space (a module identifier for the pixel-path state, installed with the zoom-state initialiser), so it cannot be used to name the token. Still open.
- Geometry-engine word 3: not examined.

What would settle the rest: the host-interface microcode read for the handler each token index jumps to (decode the 24-bit instruction word, then follow the token dispatch table), or an operand-level trace of one texture load on the model with each token removed.

### 12. Transfer mode register, bits 17 to 21

Question: positions of the unpack-order and read-mask flags. Not settled; two statements in `RE4.h` were wrong and are corrected.

- The 6.5.0 graphics library's default-state routine ORs 0x40000 (bit 18) into its transfer-mode shadow at context creation (the decompiled 6.5.0 library's default-state routine, `__glMgrasInitDefaultValues`). The header said the library never sets bit 18. The two copy initialisers (raster to raster, `__glMgrInitRSSToRSS`, and raster to texture, `__glMgrInitRSSToTE`) clear bits 17, 18, 19 and 20 one at a time and set bit 23. The DMA read helpers build their transfer mode word from the same shadow with only the format, skip and stride fields rewritten, so a GL read-back DMA carries bit 18 unless a path clears it. The "PIO read order" reading of bit 18 therefore cannot be the whole story: bit 18 is a mode flag the library sets by default and clears for copies.
- The stride-skip field is three bits wide in every writer I read (mask 0x1C000, bits 16:14; the X server uses `& 7` too), not four. Bit 17 is a single-bit flag that the same initialisers clear; nothing sets it.
- Bit 21 is never written or cleared by anything I read (library, X server, diagnostics). The diagnostics only ever set the format, type, skip and stride fields and the RGB-order bit; they never set unpack-order, zoom, decimate or read-mask.

Update: the read routine for glReadPixels (`__glMgrDoReadPixels`, 0x0da58880 in 6.5.13f, 0x0d9688d0 in 6.5.30m) is one of the paths that clears bit 18 (see entry 17), so a read through it does not carry the default.

So the unpack-order and read-mask flags are among bits 17, 18 and 21 (inferred by elimination; 19 and 20 are fixed by the trace as zoom and decimate, 22 as RGB order, 23 as opaque). Settling test: write each of bits 17, 18 and 21 on its own with a known two-pixel PIO transfer, on a board or a model, and see whether the byte order within a word, or a masked pixel, changes.

### 13. Line endpoint flags

Question: positions of the first and last endpoint flags in the instruction register. Semantics settled, positions not. The 6.5.7 diagnostic line test sets both flags to 1 exactly when line smoothing is enabled and to 0 otherwise, for the sub-pixel GL line opcode. Inferred: the flags mark the endpoints of an antialiased line for special end handling. The compiled diagnostic is stripped and builds the register with bit-field arithmetic I could not isolate, so the bit numbers are still unknown (bits 3:0 are the opcode and bit 4 is setup; the flags are somewhere above, most likely adjacent). Settling test: issue one smoothed GL line with a candidate bit set at a time in bits 5 to 8 and see which changes the coverage of the end pixels.

### 14. Crosstalk widget register defaults (Octane host interface)

Question (reset values row, narrowed): the register defaults for the Octane host interface's crosstalk widget block. The Octane build of the standalone diagnostics (`ide`, IP30 build) has a default-check table of eleven widget registers with the expected value, an access mode and a mask for each. I read the table directly out of the shipped binary (data segment at file offset 0x1431e0, 24 bytes an entry): identification 0x0E001D55 (read only, 32-bit), status 0, error address high 0 (16-bit mask), error address low 0, control 0x32F (read/write), request timeout 0xFFFFF, interrupt destination high 0, interrupt destination low 0, error command 0, link-layer configuration 0x03FF1810 (maximum burst 16, null timeout 6 in bits 15:10, retry limit 0x3FF in bits 25:16), target flush 0. Grade: established that the diagnostic expects these after power-up (it prints an error for each register that differs); inferred that they are the hardware reset values. The identification word does not decode cleanly as a standard widget identification (its part-number field is 0xE001, while the diagnostic's own part constant is 0xC003), so treat that word as the diagnostic's expectation only. Grade: unknown whether the mismatch is a different part revision, a deliberately different expectation, or a misread of the field split. Settling test: read the diagnostic's own part constant at its use site in the `ide` binary with `retools/tools/hostfacts.py`, and compare the identification register value in an existing Octane console capture of a widget probe. The host-interface registers the decode headers cover (`HQ3_DECODE.h`) are separate and stay `reset=unknown`.

### 7. Context image bank words and flags

Question: the context image's word 1 bits 26 and 28, and words 16-17 (`HQ3.h`). Settled for bit 26 and words 16-17; bit 28 narrowed. The bank-validation routine (`mgras.o`, `MgrasValidateBanks`, text offset 0x3390) writes the inverse of one field of each of the context's two draw-surface descriptors into image words 16 and 17 and sets bit 26 of word 1, for an image that is not currently loaded. When the context is loaded it sends the same two values as the arguments of the bank-validation command instead. So bit 26 means "bank words changed" and words 16-17 are the bank pair (established); that the pair names the front and back bank the next frame draws rests on the command's name and use (inferred). The old note that words 18-39 mark bit 26 is withdrawn: bit 27 is the flag for those words, in the code that copies the X server's raster state in. Bit 28 is set in the image of the kernel's own context at creation, with bit 31 (`mgras.o` context setup); a text search of the decompiled kernel objects finds no mask of that bit, so its reader is the load microcode (inferred; a shift-and-sign test would not show in a text search).

### 8. Per-engine transfers and the "late word"

Question: how the kernel addresses the second geometry engine, and why its read starts one word low. Established for the second: `MgrasEramRead` (text offset 0x1058) loops once per engine (the board's engine count byte), advancing the host buffer by the word count times four each pass, and tests bit 2 of the host address (text offset 0x11ec). When it is set it reads one word lower and one word more. The second pass starts at an odd word only because a slot is an odd number of words, so the shift is a host-buffer alignment rule, not an engine behaviour (established; replaces an inference in `GE11.h`). `MgrasEramWrite` loops the same way. Still unknown: what makes the second pass reach the second engine; it is not a command-word difference, so it is the host-interface microcode's order (see the table).

### 9. Pixel transfer zoom registers

Question: the encoding of the two zoom registers (0x154, 0x155). Narrowed. The host-to-raster setup routine in `libGLcore.so` (`__glMgrInitHostToRSS`, decompiled) writes both as 8.8 fixed point: 0x100 each with no zoom; for magnification both equal the zoom factor times 256 and the transferred width is (width x factor + 255) >> 8; otherwise the step register is (source width << 8) divided by destination width and the start register is ((source width << 8) / step - destination width) << 8 plus step. The two pairs recorded in earlier notes (0x101423AC / 0 and 0x3BFC00 / 0x1010090) do not fit this encoding and are withdrawn as register values; their source is not in this repository.

Grades, after a disassembly check of the same routine in the 6.5.0 library: established that the routine writes register 0x155 from one frame word and register 0x154 from another, and that a path stores 0x100 into both words (the no-zoom pair). Inferred, from the decompilation only and not checked against the disassembly: the magnification and shrinking formulas above. Established by a read of the 6.5.30 build of the same routine (routine facts, not a decompilation): the 0x100 pair is stored into both frame words when the word at offset 140 of the second argument equals 5, 6 or 7 (three compares at the routine's start, all reaching the same store); every other value goes on to compute the factors, where the same two words take a value from the object at offset 420 or the floating-point formulas. Established for that build. What 5, 6 and 7 stand for (a pixel-format class is the likely reading) is unknown; the test is to find who writes that word and what its enumeration is.

### 15. Display read buffer pointer word (register 0x16D)

Question: how the X server and the OpenGL library build the pointer word the raster side takes in register 0x16D, which bits pick overlay, popup or underlay planes against the main bank, which pick read against write, and whether the clip-ID fill uses a separate main pointer. Builds compared: 6.5.13f on the Octane MXI disk and 6.5.30m on the Octane SI disk (hashes in the table below).

Answer, in short: neither program builds the word from fields. The X server copies two prebuilt words, one for the main planes and one for the overlay planes, out of the video format file for the screen's mode, and writes whichever the drawing needs. The word has no plane-select or read/write bits.

Established, 6.5.13f display driver (`impactsr.so`, sha256 `ed8a8191aa08966df7f58de1731154ff5c2031cb4af6fdb991619344c4d638ec`) and 6.5.30m (`ff37f8cf23c5ab4107a06a5560da602d2d004cb648d0e55f3c1cb3da8e7e75df`):

- The screen setup routine (`mgrasInit`, 0x5e5108e0 in 6.5.13f, 0x15b8510 in 6.5.30m) keeps the two words in the screen's private record, main at +8 and overlay at +12. It first stores defaults, main 0xC8240 and overlay 0x1C0 (0x5e510aa4 and 0x5e510aac in 6.5.13f; 0x15b86ec and 0x15b86d8 in 6.5.30m), then, when the video format loader succeeds, overwrites both with the loader's results (0x5e510b2c and 0x5e510b44; 0x15b8768 and 0x15b8780). The same values are in both builds. The loader's field names are in the driver's strings: `DRBpointers_main`, `DRBpointers_overlay`, `DRBpointers_aux`, `DRB_banks`, `DIBPointer`, `DRBsize`.
- The format files are `/usr/gfx/ucode/MGRAS/vof/NAME.sdb` and, for two-raster-engine boards, `vof/2RSS/NAME.sdb`. Each is a binary record file whose field table gives each field's byte offset; the words below are read at those offsets. The files named below are byte-identical in the two builds (same sha256), so the difference the two traces show between 6.5.13f (0x380E0 overlay, 0xC8240 main) and 6.5.30m (0x101C0 overlay, 0x90240 main) is the board, not the release: the MXI disk uses the 2RSS file and the SI disk the one-engine file. That the driver picks the 2RSS directory for a two-engine board is inferred from the values matching the traces to the bit, not read from the selection code.

- Field layout the software shows (established for the two 10-bit fields, inferred for what the hardware does with them). Bits 9:0 are a page pointer (the buffer the pixel processor draws and reads), bits 19:10 a second page pointer (the second buffer of a double-buffered window). The routine that reads the frame buffer back to the host (`mgrasReadFBBlock`, 0x5e516b34 to 0x5e516b64 in 6.5.13f) loads a page pointer with `& 0x3FF`, ORs it into bits 9:0 and a copy of it, shifted left ten, into bits 19:10, and keeps bits 31:20 of the previous word (mask 0xFFF003FF). In all five rows the main word equals the low 20 bits of DIBPointer, and the overlay word's bits 9:0 equal DIBPointer bits 31:20, the overlay page. Examples: main 0xC8240 is first page 0x240 (576) and second page 0x320 (800), the second buffer 224 pages above the first; 0x90240 is 0x240 for both, so no second buffer; overlay 0x380E0 is 0x0E0 for both, 0x101C0 is 0x1C0 and 0x040. Why the one-engine overlay word carries 0x040 (64) in the second field is unknown.
- Bits 31:20 are not placed. No format file sets them. The kernel's routine for GL windows (below) leaves them as stack residue, the same defect as the size register's top byte in entry 6. That fits the window pixel buffer's pointer 0xA8000000 recorded in `MGRAS.h` (page fields 0, top byte residue); inferred.
- Plane selection is not in this word. The overlay and popup draws the question quotes (the same 0x380E0 word with ColorMaskMSBs 0x70 for one and 0xF0 for the other) differ only in the mask. The X server's screen clear routine (`mgrasClearPlanes`, 0x5e52a858 in 6.5.13f, 0x16b40b0 in 6.5.30m) writes the overlay word from +12 for the overlay case (0x5e52a8f4 loads it; mask 0xF0 at 0x5e52a918, ColorMaskLSBs A 0, fill mode 0x13F500 built at 0x5e52a97c and 0x5e52a99c) and the main word from +8 for the main case (0x5e52ab54). Popup against overlay is therefore a mask choice (0x70 against 0xF0, as `PP1.h` records) in the same word, not a pointer. Read against write buffer is the fill mode's draw field (bits 20:14) and read field (bits 25:21), as `PP1.h` records. No underlay selector exists in the pointer, the format file or these routines; underlay planes are unknown.
- The clip-ID fill is not a separate pointer. The routine that paints clip IDs (`mgrasDrawCID`, 0x5e4ff680 in 6.5.13f, 0x166e310 in 6.5.30m) and the matching path in the screen clear never write register 0x16D (no store of command word 0x00196D04 in either routine in either build). They write ColorMaskMSBs 0xFF (not "bits 1:0"; the ID, 1 to 3, goes in the fast-fill red register 0x176), pp1winmode 0xC00 and fill mode 0x142600, and draw into whatever DRBpointers value the previous draw left, which in the X server is the main word. The 0x90240 seen with clip-ID fills in 6.5.30m is the main word. Established from the machine words.

Established, kernel (`mgras.o` in `mgras.a`, 6.5.13f sha256 `7dac2718fd4662c51a9074b5728d7c5845d684933a93f9539b6fc1e4edbe8ebd`, 6.5.30m `af04a6bac1c408a0f82a4779d2b591b4d2f007c11912fabb2ed888a313de4758`): the word for a GL window is built in the kernel, not in the OpenGL library. The library never writes register 0x16D (no 0x196D or 0x596D command word anywhere in either build's `libGLcore.so`, sha256 `b1fef785cf6e1b5df097c457a3fc9c996db8e41568900534f95c10c4833c4afe` and `7030d7b17fc496001d3e0c131c943926ba38775ca8978832bdf93331056a6b4b`). The window validation routine (`MgrasValidateClip`) calls a helper (text offset 0x3180 in 6.5.13f, 0x3138 in 6.5.30m, same logic) that copies nine words of the video timing entry starting at entry offset 0x64 onto the stack, reads three nibbles of the window's packed buffer word (bits 31:28, 27:24, 23:20) and returns one of: stack word 1 when 27:24 is nonzero; stack word 2 (the main word, entry offset 0x6c, the same offset the boot-time write of 0x16D uses) when 31:28 is zero; otherwise `(stack word 10 & 0xFFFFFC00 | page A) & 0xFFF003FF | page B << 10`, where A is the low ten bits of stack word (n+2), B is the low ten bits of word (n+1) when bits 23:20 are two or more and a copy of A otherwise, and n is the sum of the two nibbles. Stack word 10 is not part of the nine copied words and nothing stores to it, so bits 31:20 of that result are leftover stack (inferred from the code of both builds). Which timing-table word is which format-file field was not matched beyond word 2, which is the main word (the boot-time write of 0x16D takes the same offset, 0x6c); stack word 1 may be the overlay word, which is unverified.

Still open: what the hardware does with the second page in an overlay word, and with bits 31:20; the underlay planes. Settling test: draw a double-buffered 12-bit window with the second page 0 and with another nonzero page and compare the two buffers; and write the register with bits 31:20 set and read the screen back.

### 16. Host transfer table slots

Question: whether a table entry for slot 0 is a byte address or a 16 KiB page address, what picks the entry format per slot, and whether the kernel writes an entry per 16 KiB page. Builds: kernel graphics modules of 6.5.13f and 6.5.30m (`mgras_dma.o`, sha256 `98a9fa327434b730754b24825c265b3a038c3dfc809320cb8463dd53119b7799` and `ff13b61214353a469a0b820a8b84f0dba2cb87cc9b30f4f6c5ec6fc6fd27de82`).

Established from the machine words (read, not executed):

- Five table slots exist. The routine that installs a table (`MgrasInstallTxTbl_Kern`, text offset 0x1a4 in 6.5.13f) refuses a slot number of 5 or more and writes, for slot s, the host-address-generator registers 0x820 + 2s (table base, physical address from the kernel's own address translation), 0x82B + s (entry count) and 0x830 + s (largest pointer offset), and register 0x84B + s. In `HQ3.h` names these are image table 1 to 3 (slots 0 to 2), the GL table (slot 3) and the display list table (slot 4). The register constants are identical in both builds (the routine differs by one branch offset); the table-fill and request-check code is structured the same in both with different register allocation, and was compared by its constants and call structure, not instruction by instruction.
- A table is a kernel allocation of at most 0x800 four-byte entries (`mgrasGetTxTbl`, text offset 0x960, 0x800 entries by default, zeroed). The base register is programmed with the table's physical address plus 12 (`daddiu 0xc` in the delay slot of the translation call at text offset 0x12d4, in the request routine `mgrasDmaUtil`, 0xdfc), so the first entry sits 12 bytes into the allocation. Xsgi's slot-0 list address ending in 0x00C fits that; whether that list is this table or the request list below is not settled.
- Entries are four bytes, one per 4 KiB page, not per 16 KiB page. The fill routine (`mgrasFillTxTbl`, text offset 0xc14) takes a start address and a length, asks the kernel for the physical page number of each 16 KiB page the range touches (`curproc_vtopv`), and writes that number and then three successors one apiece (loop at 0xc80 to 0xcd8: `+1` per entry), starting at the sub-page `(address >> 12) & 3` for the first page; after the last page it pads the rest of the table with the last entry (0xcf4 to 0xd30). So a page number a table entry holds is in 4 KiB units, four per 16 KiB page, consistent with 4 KiB page numbers like 0x56c20 in slot 3's GL lists; it is neither a byte address nor a 16 KiB page number.
- Nothing selects an entry format per slot. The slot only picks the register triple above. Slots 0 to 2 and 3 to 4 differ in the request check: the request routine, on the path taken when the flag argument has bit 2 set, rejects a request whose list holds any address with low 12 bits set (the OR of all addresses is tested against 0xFFF, text offset 0xf94, error 22), and for slots 3 and 4 it applies an extra bound, a request length above 0x0FFFFFFF is refused (compare at 0x106c to 0x107c). The request list is an array of 8-byte user virtual addresses, 4 KiB aligned; the routine builds a per-entry length array of its own in which every entry holds the request's one common length rounded down to 4 KiB (store at 0x1178), and each address and length pair goes to the fill routine (loop at 0x1148 to 0x1204). The object imports an ABI-translating copy-in, so a 32-bit caller's 4-byte entries are probably widened on the way in (inferred; the copy was not read).
- That puts Xsgi's slot-0 value 0x49e5e000 in the request list: a 4 KiB-aligned user virtual address (not 16 KiB aligned: 0x49e5e000 & 0x3FFF = 0x2000; it sits in the same 0x49e5xxxx region as the list). The zero entries behind it are unused list slots (inferred: the count is an argument, and a zero address would be translated like any other). The 4 KiB page numbers in slot 3 are the kernel's output form. This reading, not a per-slot format difference, is the proposed answer; it assumes the memory read was of the request list before the call. Settling test: read the same list after the install call and see entry 0 replaced by a page number, or read the kernel's table through the board's base register value minus 12.

### 17. Transfer mode word of glReadPixels

Question: the bits of register 0x159 for a GL read split in two parts (0xC10080 then 0xC10480; 0xC00080 then 0xC10480). Builds: `libGLcore.so` of 6.5.13f (`b1fef785...`) and 6.5.30m (`7030d7b1...`), the read routine `__glMgrDoReadPixels` (0x0da58880 and 0x0d9688d0).

Established in both builds (same instruction sequence): the routine rewrites the library's transfer-mode shadow (the word at context offset 0x9A2C) as follows: bits 3:0 from a per-context type byte (offset 0x7BF8), bits 7:4 from the low nibble of the GL format enumerant (GL_RED 0x1903 to 3 ... GL_RGBA 0x1908 to 8; 0x0DA58A20 to 0x0DA58A34), bits 10:8 cleared (mask 0xFFFFF8FF, 0x0DA5892C), bits 16:14 from a byte at context offset 0x7C1D masked with 7 (0x0DA58958 to 0x0DA5896C), and bit 18 cleared (0x0DA58960 to 0x0DA5897C). Bits 22 and 23 are left as the library default. So bit 16 is bit 2 of the three-bit stride-skip field (value 4 bytes) and 0x10000 means a stride skip of 4; no other meaning is needed. Bit 18 clear matches the observed words (0xC10080 has bit 18 clear), and settles entry 12's open question for this path: the read routine clears it. Bits 23:22 (0xC00000) are the default opaque and red-first bits.

Inferred, not read: bits 10:8 hold the low three bits of the destination address of the part (0xD68 gives 0, 0x212C gives 4, matching 0x080 and 0x480). The read routine clears the field and the code that writes it back and that splits a row into an eight-byte-aligned part and a remainder was not found in either build, so the origin of the two values and of the byte at 0x7C1D (which the observed words suggest is 4 for a row whose last part is one 4-byte pixel and 0 for a multiple of 8) is open. Test: a read to destinations with each low-three-bit value 1 to 7 and row lengths of each size mod 8, recording the words.

### 18. Two-component vertex control word (HQ command 0x59000004)

Question: what the OpenGL library sends for glVertex2s and how the host interface consumes it. Builds: both `libGLcore.so` files above.

Established: `__glMgrim_Vertex2s` (0x0dbb8958 in 6.5.13f, 0x0dac89e8 in 6.5.30m, same code) stores two words to the fixed mapping at 0x00124400: the control word 0x59000004 and the one data word `x << 16 | (y & 0xFFFF)`. `glVertex2sv` sends the same control word. Decoded with `HQ3.h`: bit 31 clear (control command), byte count 4 (one data word), command 0x000 (the vertex token), bits 22:21 clear, convert field bits 29:23 = 0x32: convert to float (bit 5), signed (bit 4), source size short (2), no normalise, no appended component. Bit 30 is also set and `HQ3.h` leaves it out. Across the 98 immediate-mode vertex, normal, colour and texture-coordinate entry points (all sizes and the array forms) the two builds give identical control words (the first word each stores, extracted from the machine words and compared with `diff`: Vertex2f 0x40000008, Vertex2i 0x58000008, Vertex2s 0x59000004, Vertex2d 0x52000010, Vertex3f 0x2000000C, Vertex3s 0x39000006, Vertex4f 0x10, Vertex4s 0x19000008, TexCoord1f 0x60000804, TexCoord2f 0x40000808), and bit 30 is set exactly in the forms that supply fewer than three components of a vertex or fewer than three of a texture coordinate (Vertex2 in all four sizes, TexCoord1 and 2), never in the three and four component forms; bit 29 (the old `HQ3.h` "append 1.0") is set for the three-component forms (Vertex3f 0x2000000C) and TexCoord1 (0x60000004). So bit 30 is a second padding flag. Its exact effect (which of z and w it supplies, and how it combines with bit 29 in TexCoord1) is inferred from the pattern only.

Not read: the host interface microcode's handling of command 0x000 and the formatter's use of the convert field, and the geometry engine's use of the vertex words. The microcode is held only as a binary listing (`hq3_revB_HQ4.u`, sha256 `deed63f3f07c5857e05c36b2ef453402336db23136c94c0c02f6b73dec800506`, 6.5.13f) that has no decoder in this repository. Settling test: decode the dispatch table entry for token 0 and the convert-field handling in that listing, or send Vertex2s and Vertex2i for one point with the two bit-30 variants through a model that decodes the convert field and compare the geometry engine's record.
